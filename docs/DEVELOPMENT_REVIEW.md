# P5-48 개발 문서·진행 방식 검토

2026-09-21. 문서 재구성 전 실제 파일·코드·Git에 근거한다. 문서 변경만 수행했으며 전체 과거 토큰/시간의 계정 원장은 확인하지 못했다. 특정 비율의 비용 낭비나 완료 일수를 추정해 확정하지 않는다.

## 확인한 문제

재구성 전 시작 안내 5개와 implementation은 합계 10,759줄·1,103,319문자였다. implementation 6,933줄, STATUS 1,552줄, HANDOFF 1,697줄에 명세와 구현 이력·실패/완료 기록이 함께 쌓였다. 현재 P5-48을 진행 중/검수 대기로 다르게 읽을 수 있는 문장도 남아 있었다. 길이뿐 아니라 반복과 시점 혼동이 문제였다.

저장소의 일반 문서는 존재만으로 매번 전부 모델 입력에 들어가지 않는다. AGENTS 지침은 자동으로 읽히며, 그 지침에 따라 문서를 도구로 열면 열린 내용이 작업 문맥에 포함된다. 따라서 모든 상세 기록을 매번 읽도록 운용하면 반복 비용과 집중할 정보의 양이 커진다. 실제 요청의 토큰 구성·캐시·압축은 여기서 계량하지 않았으므로 문자 감소를 요금 절감률로 환산하지 않는다. [공식 AGENTS 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md), [간결한 지침·읽기 경로](https://learn.chatgpt.com/docs/customization/overview#agents-guidance), [컨텍스트 압축 안내](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide#compaction).

## 이번 변경과 안전한 재개

현재 안내·분야별 요구·진행 작업의 구체적 재개 지점·과거 기록을 분리했다. 기본 파일 이름과 결정 ID, 기존 절 번호를 유지하고 기존 검토서의 anchor 링크는 이동 안내로 연결했다. 전체 기록을 새 문서에 요약 복제하지 않는다.

원문 7개를 바이트 그대로 보관하고 SHA-256을 남겼다. 읽기용 사본은 옛 상대 링크를 보정하고 당시 지시를 현재 지시로 오해하지 않도록 표시했다. 원문 전체 제목의 이동표와 기존 작업 파일별 SHA를 함께 저장했다. **코드 사본 백업이 아니라 문서 복구본과 코드 변경 여부 검증 자료**다. 기존 미커밋 작업 디렉터리를 보존해야 하며 Git HEAD로 초기화해서는 안 된다.

재개 점검은 현재 ID/상태·다음 한 작업·제외 범위·확정 정책·실제 구현 차이·마지막 검사·dirty 상태·상세 증거 위치를 짧은 안내에서 찾아 연결 경로를 확인하는 방식으로 수행했다. 정확한 크기·링크·SHA 검사 결과는 [verification.json](archive/2026-09-21-p5-48/verification.json)을 따른다.

기본 시작 안내 5개는 재구성 전 3,826줄·534,638문자에서 약 350줄·2.1만 문자로 줄었다. 상세 목차까지 포함한 6개 비교와 파일별 정확한 값은 검증 JSON에 있다. 관련 작업의 상세 명세는 별도로 더 읽는다. 전체 기록을 없앤 것이 아니며 요금/실제 사용 토큰이 같은 비율로 줄었다는 뜻도 아니다.

## 문서 밖에서 일정에 영향을 준 요인

| 관측 근거 | 판단 | 앞으로의 적용 |
|---|---|---|
| P5-31~47의 17개 작업이 생성 저장·호출 영수증·결과/비용·사람 확인·lifecycle/domain에 집중됐지만 Content Workflow는 scaffold_only다 | 필요한 기반도 있지만 사용자에게 보이는 흐름보다 내부 계층 완성을 오래 우선했다 | 기존 저장/입력/퍼즐을 연결해 실제 초안을 확인하는 흐름을 다음 구현 계획의 중심으로 삼는다 |
| P5-25 검토와 D-031이 전체 이력 반복 읽기·검사·성공 후 재조회를 줄였다 | 단순 텍스트 제품도 불필요한 반복 처리 때문에 비싸질 수 있다. 텍스트 자체가 본질적으로 무거워서가 아니다 | 새 기반을 더하기 전에 실제 요청에서 읽기/검사/저장이 중복되는지 좁게 확인한다 |
| P5-27은 실제 CPU/query·메모리 증거를 얻어 완료했다 | 과거 측정 전부가 쓸모없었다고 할 수는 없다. 완료한 실패 원인 탐색을 새 주제마다 반복할 필요도 없다 | 최종 결과를 재사용하고 관측된 회귀가 있을 때만 영향 범위를 재측정한다 |
| 정상 AI 출력 크기로 실패한 실측 없이 큰 합성 shape가 정책 논의로 확대됐다 | 가정한 극단 사례와 실제 제품 문제를 혼동했다 | 간결한 결과·구조화 검증·수동 재생성을 먼저 적용하고 새 제한/구조는 실제 필요가 확인될 때 검토한다 |
| 작은 단계마다 문서 여러 곳에 같은 구현/검사/인수인계를 누적했다 | 구현 외 반복 작업과 검토 비용이 커졌다 | 한 사실은 한 곳, 현재 안내에는 상태와 링크. 관련 검사 통과 후 근거 없는 반복 금지 |
| 기존 코드/테스트가 대량 미커밋 상태다 | 문서 정리와 별개로 HEAD만으로는 재개 자료를 복구할 수 없다 | 이번에는 파일 SHA로 무변경을 확인. 향후 사용자가 Git 저장을 진행할 때 목적별 커밋으로 복구 지점을 만들되 main push 자동 배포와 분리한다 |

이미 구현한 퍼즐·공개 풀이·제출·관리자 입력·검증과 저장 기반을 폐기하고 재작성할 근거는 없다. 코드 안전/개인정보/원자 저장 검사를 없애는 방식으로 속도를 내지도 않는다. 오래된 제품 요구와 다른 부분을 좁혀 바꾸고 완료된 부분을 재사용해야 한다.

## 앞으로 속도가 나아졌는지 판단할 기준

- 문서 재구성 효과: 매번 기본으로 읽는 파일 분량, 같은 사실의 중복 기록, 다음 작업을 잘못 재개하는 일이 줄었는가.
- 구현 순서 효과: 작업 번호/테스트 수보다 관리자가 실제 AI 초안을 보고 수정·발행하는 동작이 연결됐는가.
- 검사 효과: 문서 변경은 문서 검사, 기능 변경은 관련 테스트·lint/typecheck, Phase/배포 완료는 전체 check라는 기존 기준을 지켰는가.
- 모델/작업 운용: 모든 작은 수정에 가장 깊은 추론·다중 에이전트·전체 재검사를 습관적으로 쓰지 않았는가. 작업 위험에 맞춰 추천하고 실제 설정은 사용자의 선택을 따른다.

문서 정리는 반복 읽기와 재개 오류를 줄이는 직접 개선이다. 실제 구현 일정의 단축은 위 개발 순서와 범위 관리까지 함께 지킬 때 기대할 수 있다. 남은 구현을 실행하지 않은 시점에서 절감 시간/토큰을 보장하지 않는다.
