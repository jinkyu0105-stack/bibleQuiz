# 주요 결정 기록

> 2026-09-21 현재 제품 방향은 D-029의 P5-48 최신 기록을 우선한다. 기존 항목별 교정/최종 AI 감사에 관한 과거 결정·구현 기록은 이력으로 보존하며, 신규 흐름은 간결한 교정 문서·짧은 근거·사람 최종 검토·관리자 명시 재생성을 따른다.

> 문서 역할: 앞으로 다시 논쟁하기 쉬운 선택과 그 이유를 짧게 보존한다.  
> 상세 동작과 예외는 루트 `implementation.md`를 따른다.  
> 마지막 확인: 2026-09-21, Asia/Seoul

## 기록 규칙

- 이미 적용된 결정을 조용히 삭제하거나 반대 의미로 고치지 않는다.
- 결정이 바뀌면 기존 항목을 `대체됨`으로 표시하고 새 항목에서 이유·영향·migration을 기록한다.
- 코드가 아직 결정을 구현하지 않았다는 이유로 결정을 폐기된 것으로 간주하지 않는다.
- 가격·정책처럼 바뀔 수 있는 사실은 확인일과 공식 출처를 함께 갱신한다.

## D-001 — 상세 명세는 루트 `implementation.md`에 유지

- 상태: 채택
- 결정: 34만 자 이상의 기존 `implementation.md`를 지금 이동하거나 여러 문서로 기계적으로 분할하지 않는다. 이 파일은 상세 제품·구현 명세 정본으로 유지한다. `PROJECT_CONTEXT`, `DECISIONS`, `STATUS`, `HANDOFF`는 탐색과 세션 복구를 위한 짧은 계층으로 추가한다.
- 이유: 기존 Git 기록과 README, 대화 인수인계가 모두 현재 경로를 가리킨다. 대규모 이동은 내용 개선 없이 링크와 기준만 흔들 수 있다. 반대로 한 파일에 상태·일지·규칙까지 계속 쌓으면 새 task가 필요한 정보를 찾기 어렵다.
- 영향: 새 task는 짧은 문서들을 먼저 읽고, 작업에 관련된 `implementation.md` 절을 추가로 읽는다. 전체 상세 명세를 요약 문서에 복제하지 않는다.

## D-002 — Cloudflare Workers + Static Assets 단일 웹앱

- 상태: 채택, 기존 Pages 계획을 대체
- 결정: Cloudflare Pages를 사용하지 않고, `biblequiz-app` Worker가 React Static Assets와 Hono `/api/*`를 함께 제공한다.
- 이유: SPA와 API, D1, Workflow binding, 보안 경계를 한 배포 단위에서 명시적으로 관리하기 쉽다. 현재 규모에서는 Workers Free 범위가 충분하다.
- 영향: 옛 문서나 코드에서 Pages Functions를 새로 만들지 않는다. 다른 호스팅으로 옮길 수 있도록 핵심 도메인 로직은 Cloudflare API와 분리한다.

## D-003 — D1 + Drizzle + 검토된 SQL migration

- 상태: 채택
- 결정: 제품 데이터는 D1에 저장하고 Drizzle을 type-safe query·schema 계층으로 사용한다. schema 변경은 생성된 SQL을 검토한 뒤 환경별로 적용한다.
- 이유: 예상 규모가 작고 Cloudflare Worker와의 결합이 단순하며 무료 범위가 넉넉하다. migration을 명시적으로 보존해야 AI 중심 운영에서도 변경 이력을 복구할 수 있다.
- 영향: `drizzle-kit push`를 사용하지 않는다. Production migration은 Preview 검증·백업·대상 확인·사용자 승인을 거친다.

## D-004 — Node 24와 pnpm 11 단일화

- 상태: 채택
- 결정: local, GitHub Actions, Workers Builds 모두 Node.js 24.18.0과 pnpm 11.14.0을 기준으로 사용한다. `pnpm-lock.yaml`만 유지한다.
- 이유: 환경별 차이와 AI가 다른 package manager를 섞어 쓰는 사고를 줄인다.
- 영향: npm·Yarn 설치 명령과 다른 lockfile은 금지한다. 버전 변경은 local·CI·Cloudflare를 함께 올리고 검사 후 문서를 갱신한다.

## D-005 — Preview와 Production을 물리적으로 분리

- 상태: 채택·Preview 적용 완료
- 결정: 현재 `main`은 Workers Builds를 통해 Access 보호 `biblequiz-app-preview`와 `biblequiz-d1-preview`에만 자동 배포한다. Production Worker·D1·도메인은 아직 만들지 않는다. 비기준 브랜치 자동 Preview build는 현재 끈다.
- 이유: 코드를 직접 검토하기 어려운 운영자가 실제 서비스 반영 전에 고정 Preview에서 확인할 수 있어야 한다. 현재는 하나의 개발 브랜치와 Preview 주소가 가장 단순하다.
- 영향: `main` push는 Preview 트래픽을 바꾸지만 Production 승인이 아니다. Pull Request별 임시 URL이 실제로 필요해질 때만 non-production branch build를 다시 검토한다. **Production 준비를 시작하는 시점에는** Worker·D1·도메인을 만들기 전에 Production 배포 트리거, 운영자 승인 방식, migration 순서, rollback 기준을 사용자와 먼저 확정하고 `implementation.md`와 이 결정 기록에 남긴다. 그 합의 전에는 Production 생성·연결·migration·배포를 하지 않는다.

## D-006 — 관리자 인증은 Cloudflare Access

- 상태: 채택·Preview 적용 완료
- 결정: v1 관리자 화면과 관리자 API는 Cloudflare Access의 `Cloudflare account / Allow`로 보호한다. 현재 Cloudflare 계정 구성원은 관리자 1명이고 세션은 6시간이다.
- 이유: 자체 회원·비밀번호 시스템 없이 관리자 경계를 만들 수 있고, 관리자 API가 공개 Worker 코드에 도달하기 전에 차단된다.
- 영향: 현재 계정에 다른 구성원을 초대하면 그 사람도 Preview 접근 대상이 되므로 정책을 재검토한다. 일반 회원가입이 생겨도 Access와 D1은 대체 관계가 아니며, 관리자 Access는 별도 제거 조건을 충족할 때까지 유지한다. 첫 관리자 API인 `close-now`는 Worker 내부에서도 Access JWT의 RS256 서명·issuer·audience·시각·email을 재검증하도록 구현했다. 실제 local/Preview의 `ACCESS_TEAM_DOMAIN`·`ACCESS_AUD` 연결과 나머지 관리자 API는 후속이며, 연결 전 route는 503으로 닫힌다.

## D-007 — 일반 사용자는 회원가입 없이 익명 세션

- 상태: 채택
- 결정: v1 방문자는 회원가입하지 않는다. 서버가 발급한 브라우저 세션과 퀴즈·난이도별 제출 제약을 사용한다. 표시 입력 label은 설명을 덧붙이지 않은 `이름`이다.
- 이유: 교회 내부의 소규모 참여형 퀴즈에 회원 시스템의 운영·보안 부담이 과하다. 실명을 기술적으로 강제할 계획도 없다.
- 영향: 이름·답안·코멘트 공개·보관 동의를 받고, 문의·삭제 요청 폼과 접수번호 조회를 제공한다. 개인정보 공개 범위와 moderation은 회원가입 부재와 별도로 지킨다.

## D-008 — 성경은 개역개정 장절·판본·공식 링크만 표시

- 상태: 채택, v1 출시 게이트
- 결정: 비용을 지불하거나 별도 허가를 받지 않은 v1은 개역개정 본문 전문을 저장·복사·출력하지 않는다. 자연어 장절을 구조화하고 `개역개정` 표기와 대한성서공회 공식 읽기 링크를 제공한다.
- 이유: 관리자가 수동 복사해도 웹 공개·아카이브·인쇄 이용의 저작권 문제가 사라지지 않는다. 정확성도 AI 기억에 의존할 수 없다.
- 영향: 성경 본문을 AI가 생성·보완하지 않는다. 나중에 명시적 무료 허가 또는 적합한 라이선스가 확인될 때만 판본 레지스트리와 검수 절차를 거쳐 확장한다.

## D-009 — AI는 내용 이해, 코드는 퍼즐 배치

- 상태: 채택
- 결정: AI는 자막 교정 제안, 설교 의도·요약, 어린이용·장년용 정답 후보와 단서를 만든다. 관리자가 후보를 제외·수정·확정한 뒤, 결정론적 TypeScript 코드가 5×5~10×10 격자 크기·단어 조합·가로세로 위치·교차 밀도를 탐색한다.
- 이유: 설교 의도는 의미 판단이 필요하지만 격자 유효성·재현성·정답 비노출은 코드와 테스트가 더 정확하고 저렴하다.
- 영향: AI가 완성 격자 좌표를 최종 정답으로 결정하지 않는다. 배치기는 불가능한 조합에 이유를 반환하고 public grid와 private solution을 분리한다.

- P5-09 계약 구체화(2026-09-08): 11.4의 분석/별도 비판/사람 수정·확정을 기존 자막과 동일 집계 version/CAS의 불변 intent event로 연결한다. exact source·revision·원본/작업 checksum·confirmation·입력 version, 9개 구조화 항목·근거 구간과 네 비판 항목을 검증한다. 생성 결과는 비교 후보로 남겨 사람이 선택하며, 수정된 근거는 최종 사람 확정 동작으로 검수 기록을 남긴다. 자막이 바뀌면 과거 분석·확정을 보존하되 현재 자격은 재검토로 닫는다. 실제 AI·모델/비용·저장·UI/API·migration은 없으며 상세는 `implementation.md` 11.4의 P5-09 절을 따른다.

## D-010 — 설교 이해 품질을 AI 비용보다 우선

- 상태: 채택
- 결정: non-production에서 `gpt-5.6-terra`를 시작점으로 사용하되 설교 의도 분석과 별도의 비판 검토를 내부적으로 수행한다. 관리자 재생성 횟수와 입력·출력 token을 앱이 임의로 제한하지 않는다. 매주 누적 예상·실제 비용과 모델별 상세를 화면에 표시한다.
- 이유: 핵심 가치는 설교자의 의도를 정확히 파악한 요약과 문제 선정이다. 초기에는 관리자가 여러 초안을 비교할 가능성이 높다.
- 영향: 비용 표시와 사용자 승인 없는 모델 변경 방지는 필요하지만, 품질을 해치는 작은 token cap은 두지 않는다. Production 기본 모델 승격 전 실제 설교 품질·비용 평가가 필요하다.

## D-011 — 자막은 공개 CC 우선, 원본과 수정본을 보존

- 상태: 부분 채택·Production provider는 게이트
- 후속 정책: D-030은 입력자료 수정 대상을 자막으로 제한한다. D-031은 최초 동일 내용 수정본 생성과 매 저장 전체 이력 검사를 대체하고 diff를 요청 시 선택한 두 본문으로 제한한다. 아래 P5-07/P5-08 항목은 당시 구현 기록이며 원본·기존 이력 보존은 계속 유지한다.
- P5-05 범위 확인(2026-09-08 사용자 지시): 계정 없는 공개 자막 adapter·안전한 실패 분류는 합성 응답 기반 로컬 기술 spike로 구현한다. 기술 성공은 Production 채택·실제 콘텐츠 저장·AI·원격 설정·배포 승인으로 확대하지 않는다. 아래 원문 불변 보존은 후속 저장 구현 정책이며 P5-05는 메모리 반환만 검증한다.
- P5-06 계약 구체화(2026-09-08): YouTube 표시 스크립트는 `manual_paste + youtube_visible_transcript`로 전체/부분 coverage를 명시하고, 원고·요약본은 `sermon_notes`와 각 kind·`partial_notes`로 검증한다. 전체 원고도 전체 영상 자막으로 승격하지 않는다. 수동 원문 checksum은 무변환 UTF-8 SHA-256과 `sha256:utf8-raw-text:v1` 표식으로 정의하고 P5-05 segment JSON checksum과 구분한다. 1MiB 입력 보호 상한·strict 추가 필드 거부·원문 없는 실패/진단을 적용한다. 이는 메모리 계약이며 저장·사람 확정·UI/API는 후속이다. 부분 YouTube 스크립트의 공개 고지는 현 repository에서 미지원이므로 발행 연결 전 별도 회귀가 필요하다. 상세는 `implementation.md` 11.3의 P5-06 절을 따른다.
- P5-07 계약 구체화(2026-09-08): source 교체는 증가한 source revision, 편집·복원은 새 작업 revision을 추가하고 원본·과거 이력·확정을 보존한다. source의 기존 checksum 대상과 작업 UTF-8 checksum을 분리하며, exact 현재 source/revision/checksum과 version으로 사람 확정을 제한한다. 변경 뒤 현재 확정은 해제한다. 서버가 인증한 사람 context를 별도 인자로 받고 실제 저장 adapter에 원자적 version 비교·이력 추가·head 변경(CAS)을 요구한다. 이번 구현은 추상 port와 합성 메모리 경쟁 테스트뿐이며 실제 저장·Access 연결·UI/API·AI·migration은 아니다. 상세는 `implementation.md` 11.3의 P5-07 절을 따른다.
- P5-08 계약 구체화(2026-09-08): 선택적 제안을 exact source/원본 checksum/바탕 revision/작업 checksum에 연결하고 항목 구간·문맥·segment ID·시간을 검증한다. 미결정은 기록 없음으로 표현하고 수락/거절은 재결정 없는 불변 batch로 남긴다. 별도 명령이 수락 항목만 바탕 offset 역순으로 재현해 새 merged revision을 만들며 사람 확정을 해제한다. 제안·결정은 자동 적용하지 않고 집계 version/CAS로 동시 결정·편집·병합 충돌을 차단한다. 직접 수정·확정은 AI 없이 유지한다. 실제 AI/저장/UI/API/migration 없이 기존 계약을 확장한 것이며 상세는 `implementation.md` 11.3의 P5-08 절을 따른다.
- 결정: 계정 연결 없이 공개 CC 데이터를 가져오는 adapter를 우선 시험한다. 성공한 원문은 불변으로 보존하고, 사람 직접 수정 후 바로 확정하거나 AI 오타 교정 제안과 diff를 검토한 뒤 사람이 최종 확정한다. 자막이 없거나 provider가 실패하면 텍스트 직접 붙여넣기를 무료 fallback으로 제공한다.
- 이유: 교회 YouTube 계정 권한과 자막 파일을 받을 수 없는 현재 운영 여건에서도 작업을 시작해야 하며, 발음 오류를 사람이 통제할 수 있어야 한다.
- 영향: 비공식 YouTube 음원 다운로드를 production 기능으로 만들지 않는다. 원본 음성 파일을 합법적으로 제공받는 별도 상황에서만 유료 AI 전사를 다시 검토한다.

## D-015 — 작은 화면에서는 칸을 줄여 퍼즐 전체 표시

- 영향: 셀은 일반 최대 96px, 크게 보기 최대 112px 범위에서 컨테이너 폭/격자 칸 수로 계산한다. 작은 셀의 번호·입력 글자·방향 기호도 비례 배치한다. 일반 조작 버튼의 최소 44px, 이전/다음·방향 버튼의 최소 48px는 유지하고 단서 선택·키보드 입력으로 작은 셀 누르기를 보완한다. 크게 보기에서도 전체 격자가 잘리거나 가로 스크롤이 생기지 않는다.
- migration: 데이터·DB 변경 없음. 화면 CSS·가로 이동 코드·크기 회귀 테스트만 변경하며 실제 기기 입력/접근성 검증은 별도로 남긴다.

## D-016 — 조합 중 명시적 클릭은 취소 후 이동

- 상태: 채택, 2026-09-01 사용자 명시 승인
- 결정: 한글 IME 조합 중 자동 이동·앱이 처리하는 키보드 이동·임시 저장은 계속 막는다. 다만 사용자가 다른 격자 셀이나 난이도 탭을 마우스·터치로 명시적으로 클릭하면 미확정 조합을 취소하고 선택한 대상으로 이동한다. 확정된 음절은 유지하고 미완성 자모는 저장하지 않는다.
- 이유: Windows Chrome 실제 확인에서 미완성 `ㄹ`을 클릭으로 취소하고 이동하는 동작이 자연스럽다고 사용자가 판단했다. 모든 이동을 잠그는 보수적 규칙보다 사용자의 명시적 선택을 우선하면서도, 자동 이동·저장에 따른 중복·오배치·손상 위험은 계속 막는다.
- 영향: pointer 기반 셀 선택·난이도 탭 전환은 조합 취소 뒤 수행해야 한다. 합성 이벤트 회귀와 실제 브라우저 확인은 이 경계를 분리해 검증한다. 이후 코드와 기존 `조합 중 이동 차단` 테스트를 이 결정에 맞게 정합화했고 Windows Chrome/Edge와 자동 브라우저 회귀로 확인했다.

## D-017 — iPhone 길게 누르기 붙여넣기는 v1 게이트에서 제외

- 상태: 채택, 2026-09-01 사용자 명시 승인
- 결정: 한글 직접 입력·수정·삭제와 모바일 이동·방향 전환은 v1 필수다. 데스크톱 `Ctrl/Cmd+V`와 운영체제가 실제 `paste` 이벤트를 전달하는 경로는 계속 지원하지만, iPhone의 활성 격자 칸 길게 누르기 편집 메뉴는 지원 보장·Phase 3 통과 조건에서 제외한다. 별도 `붙여넣기` 버튼은 실제 사용자 요구가 확인되기 전에는 추가하지 않는다.
- 이유: 붙여넣기는 모바일 퀴즈 풀이의 핵심 입력이 아니라 편의 기능이다. 투명한 단일 native input 위에 iOS 편집 메뉴를 강제하거나 Clipboard API 버튼을 추가하면 안정화된 한국어 IME·터치 조작을 다시 복잡하게 만들고 권한·UI 부담도 늘어난다.
- 영향: iPhone Safari·Chrome에서 길게 누르기 메뉴가 나타나지 않아도 직접 입력·수정·삭제·스크롤·방향 전환이 정상이면 기기 행렬 실패로 세지 않는다. 기존 paste reducer·DOM 이벤트·데스크톱 실제 clipboard 검사와 초과 안내는 유지한다.

## D-018 — 제출 재시도는 실제 내용 기준으로 재생

- 상태: 채택
- 결정: 같은 quiz variant·session·UUIDv7 idempotency key의 재시도는 NFC/trim된 이름·코멘트와 canonical key 순서의 sparse cells, revision·동의가 같으면 저장된 성공 결과를 재생한다. request hash에서 idempotency key와 Turnstile token은 제외한다. 기존 성공 확인은 새 moderation 규칙과 Siteverify보다 먼저 수행한다.
- 이유: Turnstile token은 짧게 유효하고 한 번만 쓸 수 있어 정상적인 네트워크 재시도에서 새 token이 필요할 수 있다. 이미 성공한 요청을 이후 정책 변경으로 실패시키거나 token을 다시 소비하면 멱등성이 깨진다.
- 영향: 같은 key로 실제 제출 내용을 바꾸면 `IDEMPOTENCY_CONFLICT`, 다른 key로 같은 variant에 다시 제출하면 `ALREADY_SUBMITTED`다. 삭제 tombstone도 재제출을 허용하지 않는다. 신규 요청만 현재 moderation·Turnstile을 통과하며 D1 UNIQUE는 동시 요청의 최종 방어선으로 유지한다.

## D-019 — 본인 제출 복원은 exact session의 최소 응답

- 상태: 채택
- 결정: `GET /api/quizzes/:slug/:difficulty/me`는 현재 공개 가능한 exact variant와 현재 브라우저의 active 익명 session만 사용하고 `private, no-store`로 응답한다. cookie 없음·오류·미등록·만료·미제출은 session 생성이나 touch 없이 null이다. visible·hidden 제출은 소유자에게 variant/revision·답안·서버 결과만 반환하고, deleted는 답안·정답 없는 tombstone만 반환한다. 이름·코멘트·session hash·idempotency/request hash·moderation 상태는 어느 응답에도 넣지 않는다. submitted 결과는 현재 canonical private source로 재채점해 저장값과 일치할 때만 복원하며, 조회 실패 시 브라우저는 새 제출을 잠근다.
- 이유: 공개 퀴즈 GET에 정답을 섞지 않으면서 새로고침과 재방문 결과를 복원해야 한다. hidden은 다른 사용자에게서 숨기는 moderation 상태이지 소유자가 이미 받은 결과를 취소하는 상태가 아니고, deleted는 삭제한 개인정보·답안·정답을 되살리면 안 된다. 소유권을 확인하지 못한 순간 새 제출을 허용하면 중복·충돌을 유발한다.
- 영향: 참여 현황 board는 아래 D-020의 별도 계약으로 구현했다. 제출 수·본인 삭제·지난 퀴즈 연습 채점과 Top N 화면/출력은 계속 별도 작업이다. 본인 복원은 published/archived의 공개 active variant만 지원하며 superseded 오류본 소유자 접근은 관리자 수정 workflow와 함께 별도 확장한다. D-019 자체의 데이터 migration과 원격 환경 변경은 없다.

## D-020 — 참여 현황은 상태별 접근과 고정 순위를 분리

- 상태: 채택
- 결정: `GET /api/quizzes/:slug/:difficulty/board`는 현재 공개되는 exact active variant만 `private, no-store`로 읽는다. 진행 중 `published` board는 같은 variant에 visible 또는 hidden 제출을 가진 active 익명 session만 열 수 있고 deleted·미제출 session은 거부한다. `archived` board는 session 없이 공개한다. 공개 참여자는 visible 제출만 제출 시각·ID 순으로 내보내고, session hash·DB ID·idempotency/request hash·moderation/관리자 정보는 제외한다. 서버는 공개 geometry와 비공개 solution으로 각 visible 답안을 다시 채점해 저장 점수와 일치할 때만, 정답 자체 대신 `correctCellIds`를 내보낸다. 순위는 같은 응답의 참여자를 `{rank, submissionOrder}`로만 참조한다. 진행 중에는 완전 정답 visible 제출로 동적 계산하고, archived valid 퀴즈는 마감 시 저장된 snapshot만 읽는다. 이후 hidden/deleted가 된 수상자는 제외하되 다음 사람을 승격하지 않아 rank 빈자리를 보존한다. 브라우저는 published에서 제출 결과가 확인되기 전 board를 요청하지 않고, published·archived 모두 사용자가 `참여 현황 보기`를 선택한 뒤에만 읽는다. `Top N`은 이 검증된 board를 화면에서 다시 투영하며 독립 `GET /top-n`은 만들지 않는다. 출력만 `GET /top-n-export`를 별도 경계로 둔다.
- 이유: 제출 전 정답 공유를 줄이면서 제출자는 진행 중 참여 답안을 함께 볼 수 있어야 하고, 마감 후 순위는 이후 moderation·삭제로 다른 참가자의 순위까지 바뀌면 안 된다. 공개 표시 필드와 소유권/운영 필드를 계약 단계에서 나누고 순위에 개인정보를 중복하지 않으면 누출·불일치 표면이 작아진다. 이미 같은 접근 권한·snapshot으로 받은 `participants`와 `winners`를 다시 계산하는 endpoint를 두지 않으면 순위 불일치와 불필요한 요청도 줄일 수 있다.
- 영향: archived valid 퀴즈에 snapshot이 없거나 저장 revision·점수·답안·순위 관계가 손상되면 임의 재계산하지 않고 503으로 닫는다. non-ranked correction은 제출이 전혀 없는 새 revision만 빈 board로 공개한다. on-demand 참여 현황 화면은 실제 답안과 정답·다른 답·빈칸, 본인 표시를 제공하되 private solution은 받지 않는다. 구현된 Top N 화면은 완전 정답자만 남기고 `winners`가 참조한 카드에만 rank를 붙이며, 추가 요청 없이 N위 밖 완전 정답자를 유지하고 코멘트를 숨긴다. 출력용 응답에도 부분 답안·코멘트를 다시 넣지 않는다. 공개 퀴즈의 visible 제출 수는 exact active variant revision만 따로 검증해 표시하며 hidden·deleted·집계 손상은 0명으로 바꾸지 않는다. `0004_phase4_leaderboard_snapshot.sql`, 아래 D-022의 원자적 writer와 공개 lazy·scheduled·관리자 즉시 마감 호출 경로를 구현했다. `0005_phase4_audit_logs.sql`은 관리자 즉시 마감과 본인 삭제 감사를 원자적으로 남기며, D-024의 최종 purge·복원 경계도 같은 표를 PII 없는 manifest 원본으로 사용한다. Top N 출력은 후속 작업이다. 두 migration은 격리 D1에서만 검증했고 원격에는 적용하지 않았다.

## D-021 — 본인 삭제는 exact owner의 멱등 tombstone 변경

- 상태: 채택
- 결정: `DELETE /api/quizzes/:slug/:difficulty/me/submission`은 same-origin `application/json`의 strict 빈 객체 `{}`와 현재 공개 가능한 exact variant의 active 익명 session만 받는다. visible·hidden 본인 제출은 이름·코멘트·실제 답안을 한 D1 batch에서 제거하고 deleted tombstone으로 바꾼다. 동시·반복 삭제는 최초 `deletedAt`의 같은 최소 성공 응답을 반환한다. 미제출 session은 404, 없거나 만료된 session은 401로 닫는다.
- 이유: 삭제 재시도 중 네트워크 응답이 유실되어도 사용자가 실패로 오해하지 않아야 하며, 다른 session·난이도·revision의 기록을 건드리거나 삭제된 개인정보·정답을 응답으로 되살리면 안 된다.
- 영향: 성공 응답에는 `status`, variant ID/revision, 삭제 시각만 있으며 이름·코멘트·답안·solution·session/idempotency/request hash·moderation 상태를 넣지 않는다. 점수와 중복 방지용 내부 열은 공개하지 않은 채 행에 남아 재제출을 `ALREADY_SUBMITTED`로 막는다. 최초 변경은 `self_service`·email 없음·variant/revision/삭제 시각만 담은 감사 행과 같은 D1 batch로 확정하고, 감사 실패에는 개인정보 제거와 session touch도 rollback한다. D-019에 따라 archived 본인 조회도 tombstone을 반환하므로 archive 순간 자동 제거하지 않으며, D-024의 명시적 최종 purge 전까지 유지한다. 기존 `0005` schema로 충족되어 새 migration과 원격 변경은 없다.

## D-022 — 마감 순위와 archive 전환은 하나의 조건부 D1 batch로 확정

- 상태: 채택
- 결정: `finalizeDueQuizSet`은 마감된 published 세트의 exact active valid 어린이용·장년용 variant와 저장 결과를 먼저 검증한다. 그 뒤 visible 완전 정답자를 제출 시각·ID 순으로 난이도별 `winner_count`만큼 snapshot에 넣고, 두 snapshot과 모든 rank entry가 성공한 같은 D1 batch의 마지막에서만 세트를 archived로 바꾼다. 각 statement는 due published 상태와 exact variant를 다시 조건으로 확인하며 반복·동시 실행은 기존 immutable snapshot을 검증해 replay한다.
- 이유: snapshot 일부만 생성되거나 archive만 먼저 확정되면 마감 결과를 복구하기 어렵다. scheduled·lazy·관리자 즉시 마감은 서로 경쟁할 수 있으므로 애플리케이션의 사전 조회만으로는 한 번 실행과 제출 경계를 보장할 수 없다.
- 영향: 제출 insert도 같은 DB 쓰기 경계에서 `published + open`, exact active valid revision과 `opens_at <= now < closes_at`을 확인한다. 사람 확인 중 마감을 넘긴 신규 제출은 저장되지 않지만 이미 저장된 같은 요청의 replay는 유지한다. 공개 quiz GET·board·본인 조회/삭제·제출의 lazy resolver, due 세트를 안정 순서로 처리하는 scheduled handler, Access JWT와 확인·사유를 검증하는 관리자 `close-now` route가 모두 같은 writer를 호출하도록 구현했다. 즉시 마감은 `closes_at`, 두 snapshot, archive, `0005` 감사 로그를 한 D1 batch로 확정한다. 실제 Cron trigger와 환경별 Access 변수, 관리자 UI는 아직 연결하지 않았고 migration·원격 환경도 변경하지 않았다.

## D-023 — Phase 작업은 고정 번호·한도 게이트·검증된 세션 경계로 추적

- 상태: 채택, 2026-09-03 사용자 명시 승인
- 결정: 남은 작업은 `P4-17` 형식의 고정 Phase ID로 `STATUS`의 활성 목록과 `HANDOFF`의 정확한 재개 지점에 함께 기록한다. 한 번호는 구현·필수 검사·상태 문서가 끝날 때만 완료이며, 후속 구현·검수·실패가 남으면 같은 번호를 유지한다. 사용자의 `시작하세요`는 현재 번호 한 작업만 의미한다. 한도에 맞춘 하위 단계는 `P4-17a`처럼 부모 번호에 속하며, 한도 복구 뒤에도 미완료 부모부터 다시 시작한다.

## D-024 — 삭제 manifest는 PII 없이 복원 전 재적용하고 tombstone은 명시적 종료 경계에서만 purge

- 상태: 채택
- 결정: 본인 삭제의 `self_service_delete` 감사 행을 삭제 manifest의 D1 원본으로 사용한다. 별도 private object에 저장할 manifest v1은 `auditId`, `submissionId`, `quizVariantId`, `quizRevision`, `deletedAt`과 object 생성 시각만 가지며 이름·코멘트·답안·session hash·request/idempotency hash·점수를 포함하지 않는다. 과거 backup을 복원한 뒤에는 public traffic을 열기 전에 이 manifest를 항목별 D1 batch로 재적용해 제출을 deleted/PII-null로 만들고 snapshot 참조를 제거하며, 모든 항목이 `삭제 tombstone 또는 행 없음 + exact self_service 감사 + snapshot 참조 없음`인지 별도 hard gate로 다시 검증한다. 중간 실패에는 공개를 계속 닫고 같은 manifest를 멱등 재실행한다.
- 이유: backup 자체에는 삭제 뒤의 최신 상태가 없을 수 있고, DB 안의 tombstone만 믿으면 과거 이름·답안·코멘트가 복원과 함께 다시 공개될 수 있다. 반대로 manifest에 session hash나 파생 hash를 복사하면 별도 장기 보존 개인정보가 생긴다. 복원 적용과 공개 재개 검증을 분리하면 부분 적용이 있어도 개인정보가 공개되는 것을 막을 수 있다.
- 영향: ordinary archive·마감·시간 경과에는 tombstone을 자동 제거하지 않는다. 최종 purge는 `site_shutdown`, `archive_disposal`, `privacy_purpose_ended` 중 하나의 명시적 사유와 exact manifest 항목을 서버 전용 service에 전달할 때만 실행한다. 이때 snapshot 참조, submission 전체 행, 다른 제출이 없는 orphan 익명 session을 같은 D1 batch에서 제거하고 PII 없는 `system` purge 감사를 남긴다. 공개 route·Cron·관리자 원클릭 UI는 만들지 않았고 실제 private R2 object 저장·D1 restore runbook 실행은 Phase 8의 별도 승인 작업이다. 기존 `0002`·`0004`·`0005`로 구현되어 새 migration·원격 적용·배포는 없다.

## D-025 — 관리자 submission moderation은 exact 상태 전이와 복원 안전 삭제를 한 batch로 확정

- 상태: 채택
- 결정: Access 인증 뒤 `PATCH /api/admin/submissions/:id`는 `visible→hidden`, `hidden→visible`만, `DELETE`는 `visible|hidden→deleted`만 수행한다. 이미 같은 관리자 조치로 목표 상태가 된 요청은 새 기록 없이 replay하고, 처음부터 목표 상태였거나 본인 삭제로 deleted가 된 대상은 상태 오류로 닫는다. 최초 변경은 PII를 가진 `moderation_actions`, `access_admin` audit, submission 변경을 한 조건부 D1 batch로 확정한다. 관리자 delete는 여기에 PII 없는 `system` 삭제 표식을 함께 기록하며, deletion manifest는 `deletionSource`로 self-service 감사와 관리자 표식을 구분한다.
- 이유: UI나 route 검증만 믿으면 service 직접 호출·동시 요청에서 상태와 감사 기록이 갈릴 수 있다. 관리자 삭제도 과거 backup에서 이름·답안·코멘트가 되살아날 수 있지만, Access 이메일과 사유를 장기 manifest에 복사하면 별도 개인정보 보존면이 생긴다. 따라서 복원용 표식과 운영자 감사 기록을 분리한다.
- 영향: `0006_phase4_submission_moderation.sql`이 FK를 가진 `moderation_actions`를 추가한다. 최종 purge는 해당 submission의 moderation action과 `access_admin` audit도 submission 전에 제거하고 PII 없는 삭제 표식·system purge 감사만 유지한다. published board는 현재 visible 집합으로 다시 순위를 계산하고, archived snapshot 행은 moderation 때 보존해 hidden/deleted rank만 비우며 unhide 시 원래 rank를 복원한다. 관리자 목록/UI, 실제 Access 변수, local/Preview/Production migration·배포는 포함하지 않는다.

- 결정: ① 처음 가져온 자막은 원본만 저장하고 실제 수정 내용을 저장할 때 수정본을 추가한다. ② 새 수정본 저장은 입력 내용·설교 ID·현재 수정번호와 이번 명령에 필요한 자료만 검사하며 과거 전체 본문 재검증을 일반 저장 경로에서 제외한다. ③ 원자 쓰기의 정상 성공이 확인되면 본문 재조회·비교는 0회이며, 결과가 불분명할 때만 해당 저장 건을 확인한다. ④ diff는 비교를 요청한 시점에 선택한 두 본문만 대상으로 계산하고 저장 때 미리 만들지 않는다.
- 이유: 저장 공간보다 반복 읽기·복사·검증·전송이 현재 CPU 부담을 만든다. 원본/수정 이력과 실제 필요한 안전장치는 보존하면서 요청 하나가 처리하는 양을 줄인다. 초기 이력 없는 저장도 실패했으므로 보관 개수 제한만으로 해결하지 않는다.
- 폐기: `현재 수정본 1개 + 직전 2개`만 보존하고 나머지를 자동 삭제하는 안은 채택하지 않는다. 후속 후보로 자동 재개하지 않으며 기존 이력을 삭제하지 않는다. 별도 기존 초안 7일 정리·source별 보존 정책을 취소하거나 영구 무제한 보존을 새로 약속하는 결정도 아니다.
- 유지: D-030의 자막만 수정/목사님 제공 원고·요약본 원문 사용, 입력 유효성·인증/소유권·현재 version 확인, 원자 저장·충돌 시 무기록·실패 rollback, 과거 이력·사람 검수·상위 변경 시 재검토·공개 비노출. 과거 전체 손상은 매 저장 자동 검사 대신 별도 전체 검사에서 발견할 수 있다는 경계 변경을 명시한다.
- 구현 경계: 정상 성공은 단순 `success: true`가 아니라 전체 batch 응답의 개수와 각 `success`/정수 `meta.changes`가 쓰기 계획에 정확히 일치하는 경우다. 기존 0008/bound verified 경로는 수정하지 않고 0009로 `sermon_input_events/chunks/heads`를 추가했다. 새 경로는 단일 원자 batch와 deferred seal/불변/소유권/공유 version 제약으로 보호하며, 정상 성공 때 원래 본문을 DB로 재전송해 대조하지 않는다. 불확실한 응답은 자기 event의 metadata와 모든 TEXT 조각을 기대 문자열과 정확히 비교하고 자동 replay하지 않는다. 새 경로는 원본 또는 실제 수정본을 `documentId`로 지칭하며 기존 전체 state를 부분 배열로 위장하지 않는다. 같은 설교에 기존/새 head가 공존하는 것은 DB에서 양방향 차단한다. 원격·Production·실제 콘텐츠·새 서비스·Paid·checkpoint/staging·전체 runtime/Workflow/UI/API는 추가 승인 범위에도 없다.
- 상세: [implementation 저장 처리 범위](../implementation.md#저장-처리-범위-축소--2026-09-15-확정), [P5-27 최신 적용 상태](P5-27_STORAGE_REVIEW.md#0-d-031-확정과-적용-범위).
- P5-29 조회 구체화(2026-09-17): 현재 source event metadata 목록은 512건으로 제한하고 actor·본문/chunk·excerpt·hash·byte 정보를 SQL/DTO allowlist에서 제외한다. 비교는 명시한 두 document만, 교정 상세는 선택 proposal과 연결 decision만 bounded하게 읽는다. 전체 이력 본문 replay·diff 계산·화면·새 schema/migration은 추가하지 않았다. 상세는 [implementation 14.3.14](../implementation.md#14314-p5-29-비공개-입력자료-이력선택-상세-조회-api--2026-09-17)를 따른다.
- P5-30 화면 구체화(2026-09-17): `/admin`은 current와 metadata 이력의 head 일치를 확인한 뒤 최초 원본·편집·확정·복원·수동 교정 제안/결정/병합을 기존 API로 호출한다. 비교는 사용자가 고른 두 document를 받은 뒤에만 브라우저 메모리에서 bounded diff를 계산하고 저장·로그에 남기지 않는다. proposal은 상세 버튼을 누른 한 건만 읽는다. 실제 AI·Workflow·source 교체·schema/migration·원격 적용은 추가하지 않았다. 상세는 [implementation 14.3.15](../implementation.md#14315-p5-30-access-관리자-입력자료-화면-연결--2026-09-17)를 따른다.

## D-032 — P5-27 메모리 검증을 로컬 동시 부하와 원격 지표로 분리

> 후속 D-033은 설교 자막 입력 상한과 경계 시험 분량만 대체한다. 아래 입력 축소 미승인은 D-032 당시 범위이며 D-033 승인 이후 자막에는30,000자 기준을 적용한다. 메모리 검증 방법과 CPU/query 목표는 유지한다.

- 상태: 채택, 2026-09-16 사용자 `네 그렇게 하세요` 승인. 검증 방법 변경이며 측정 통과나 P5-27 완료 승인이 아니다.
- 결정: 원격 순간 isolate peak 직접 증명 요구를 `로컬 동일 isolate의20개 동시 invocation 상세 heap 관측 + 해당 Preview 시험의 원격 메모리 지표와 메모리 초과 오류 확인`으로 대체한다. 로컬/원격 수치를 분리하며 어느 것도 정확한 원격 순간 최대값이라고 표현하지 않는다.
- 이유: Access 로그인은 성공했으나 설치 Wrangler4.125.0이 remote inspector를 비활성화한다. 공식 Metrics는 invocation 시점 표본 percentile이며 순간 최대값이 아니다. 같은 로그인/연결을 반복하지 않는다.
- 적용: 기존96MiB 여유 예산을 유지해 로컬 관측량과 원격 제공 지표를 각각 대조한다. 로컬은 JS heap·backing storage·embedder를 별도 기록하고 예약된 total heap까지 포함한 보수적 합계를 병기한다(플랫폼 전체 메모리와 동일하지 않음). 원격은 실제 제공 percentile/시간창/대상 version/누락을 명시한다. 수집 불가/표본 없음/오류 분류 불가는0 또는 통과가 아니라 미확인이다. 원격 메모리 초과0건 확인도 유지한다.
- 유지: CPU 전형/경계 각100회 p95≤7ms/max≤9ms·query≤40·20개 동시 실행·CAS/무기록/rollback/기존 의미 회귀. 첫 표본 제외·입력 축소·이력 삭제·Paid·새 서비스·Production·공유DB 쓰기·runtime/Workflow/UI/API·새 schema/migration은 승인하지 않는다. 기존 계측과 P5-23~P5-26 완료 기록을 보존한다.
- 상세: [implementation 메모리 검증](../implementation.md#p5-27-메모리-검증-방법-변경--2026-09-16-d-032).

## D-033 — 설교 자막 최대 3만 자

- 상태: 채택, 2026-09-16 사용자 `3만자 분량으로 정해` 명시 확정 후 새 비공개 저장 경로에 적용·로컬 경계/회귀 검증했다. 일반/준비 완료 import·교체·직접 수정·복원·AI merge에 적용하며 기존 자료 reader·목사님 제공 자료의 한도는 보존한다. P5-27 원격 계측과 D-032 메모리 검증을 통과했고, P5-28의 Access 관리자 최초 저장·자막 변경 API에도 연결했다. 사진 직접 관측 P9996.84MB·버전 사용자 확인과 검사 결과는 STATUS/HANDOFF 및 [완료 보고서](P5-27_CAPTION_30000.md)를 따른다. UI/Workflow·실제 콘텐츠·원격 migration/배포는 미실행이다.
- 결정: 설교 자막 원본과 신규 수정 결과의 본문을 공백·줄바꿈 포함30,000 Unicode code points 이하로 제한한다. 정확히30,000자 허용,30,001자부터 저장 전 거부하며 자르거나 자동 요약하지 않는다. 공개/붙여넣기 자막에 적용하고 목사님 제공 원고·요약본의 기존 정책은 자동 변경하지 않는다. 기존 원문/수정 이력도 삭제하지 않는다.
- 이유: 사용자가 필요한 지원 분량을 직접 제한했다. 종전200KB 합성 입력을 계속 최적화하기보다 승인한 제품 상한을 먼저 적용하고 그 경계에서 검증한다. 한글 위주 약90KB라는 환산은 참고일 뿐 byte 상한이나 CPU 통과 보장이 아니다.
- 영향: 같은 P5-27의 다음 작업을30,000자 제한 적용·로컬 경계 검사로 바꾸고 Zod 교체/컴파일 시험은 보류한다. 전형/경계 각100회·20개 동시, CPU7/9ms·query40·D-032 메모리96MiB·기존 의미 회귀는 유지한다.200KB/1MiB 과거 결과와 P5-23~26 완료 기록은 보존하며 새 성적으로 재분류하지 않는다. 이 결정만으로 배포·DB/schema·전체 runtime·새 의존성 변경을 실행하지 않는다.
- 상세: [implementation 자막 상한](../implementation.md#설교-자막-최대-3만-자--2026-09-16-d-033). 한도 계수·구간 본문 연결·Unicode/byte 보호·기존 이력 보존 경계를 따른다.
