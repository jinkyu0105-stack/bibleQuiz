# 향후 검토 기록

> 상태: v1 범위 밖의 검토 기록. 현재 인증·권한 계획을 변경하지 않는다.
>
> 현재 v1은 일반 사용자 회원가입 없이 운영하며, Preview 관리자 영역은 Cloudflare Access의 `Cloudflare account / Allow`로 보호한다. 현재 계정 구성원은 운영자 1명이다. 향후 Cloudflare 대시보드 권한 없이 사이트 관리자 기능만 사용할 사람을 추가할 때에만 정확한 이메일 허용 목록과 이메일 일회용 코드를 대안으로 검토한다.

## 1. 이 문서를 남기는 이유

향후 일반 사용자 회원가입을 받거나 교회 공식 사이트의 회원 체계를 연동할 때 `Cloudflare Access를 없애야 하는가`, `D1으로 갈아타야 하는가`, `기존 회원 DB를 그대로 가져올 수 있는가`를 다시 처음부터 판단하지 않기 위한 기록이다. 실제 확장 시점에는 당시의 서비스 가격·보안 기준·교회 승인·기존 사이트 구조를 다시 조사하고 결정한다.

## 2. Access와 D1은 대체 관계가 아니다

- **Cloudflare Access**: 관리자처럼 제한된 사람만 비공개 화면과 API에 들어오게 하는 외부 인증 관문이다.
- **D1**: 회원·프로필·역할·참여 기록·애플리케이션 세션 같은 데이터를 저장하는 SQL 데이터베이스다.
- **회원 인증 계층**: 비밀번호, 이메일 링크, 소셜 로그인, OIDC/SAML 등을 실제로 검증하고 세션을 발급하는 코드 또는 인증 서비스다. D1만 추가한다고 이 계층이 자동으로 생기지는 않는다.

## 3. 일반 사용자 회원가입을 추가하는 경우

권장 기본 구조:

```text
일반 회원
  → 회원 인증 계층
  → 회원용 API
  → D1의 회원·프로필·참여 기록

관리자
  → Cloudflare Access
  → 관리자 API
  → D1의 운영 데이터·감사 기록
```

D1에는 필요에 따라 `users`, `user_profiles`, `auth_identities`, `roles`, `user_sessions`, 회원별 참여 기록을 추가한다. 평문 비밀번호는 절대 저장하지 않는다. 비밀번호 로그인을 직접 운영한다면 검증된 인증 라이브러리, 강한 password hashing, 재설정·세션 폐기·rate limit·MFA까지 함께 설계해야 한다. 이메일 링크나 외부 인증 제공자를 쓰면 발송 비용, 무료 한도, 계정 복구와 서비스 종속성을 먼저 비교한다.

### 관리자 인증 권장안

일반 회원가입이 생겨도 관리자 로그인은 당분간 Access에 남긴다.

- 일반 회원 계정 탈취나 회원 인증 코드의 결함이 관리자 권한으로 이어지는 것을 분리한다.
- 일반 회원 API는 앱 회원 세션과 데이터 소유권을 검사한다.
- 관리자 API는 Access JWT의 서명·issuer·audience를 검증한다.
- 관리자가 일반 기능도 쓸 때는 일반 화면에서는 회원으로 이용하고 `/admin` 진입 시 Access를 추가로 통과할 수 있다.

Access는 회원가입 기능이 생겼다는 이유만으로 제거하지 않는다. 자체 인증이 관리자 MFA, 역할·권한, 계정 회수, 감사 기록, 관리자 API 분리, 보안 테스트까지 충분히 대체한 경우에만 제거를 검토한다.

## 4. 교회 공식 사이트 회원을 승계하는 경우

기술 작업 전에 교회가 이 개인 프로젝트로 어떤 개인정보를 어떤 목적으로 이전하거나 연동해도 되는지 명시적으로 승인해야 한다. 필요한 정보만 사용하고, 공식 사이트 DB에 이 앱이 직접 상시 접속하는 구조는 피한다.

### A. 공식 사이트가 OIDC 또는 SAML을 제공하는 경우 — 최우선 권장

회원 DB와 비밀번호를 복사하지 않고 공식 교회 계정으로 로그인한다. 로그인 결과의 안정적인 외부 사용자 ID를 이 앱의 D1 프로필과 연결한다.

```text
사용자 → 교회 공식 인증 → 검증된 identity claim → D1의 로컬 프로필
```

장점:

- 기존 비밀번호를 가져오지 않는다.
- 사용자는 계정을 새로 만들지 않아도 된다.
- 공식 사이트에서 계정이 중지될 때 연동 정책을 적용할 수 있다.
- 관리자도 같은 공식 인증원을 사용하되 Access 정책으로 관리자만 별도 허용할 수 있다.

Cloudflare Access는 일반 OIDC와 SAML 2.0 identity provider를 연동할 수 있다. 그렇다고 모든 교인을 Access 사용자로 넣는 것은 아니다. 일반 교인은 앱의 공식 계정 로그인 흐름을 사용하고, 관리자는 같은 인증원을 쓰더라도 Access 보호 경로를 추가로 통과하는 구성을 우선 검토한다.

공식 참고:

- [Cloudflare Access Generic OIDC](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/generic-oidc/)
- [Cloudflare Access Generic SAML](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/generic-saml/)

### B. 공식 사이트에서 회원 데이터를 내보내 받는 경우

이름·회원번호·이메일·상태 같은 승인된 최소 필드는 변환·검증 후 D1로 이전할 수 있다. 비밀번호는 별도로 판단한다.

- 평문 비밀번호는 받거나 이전하지 않는다.
- password hash도 algorithm·parameter·salt·pepper와 기존 구현이 호환되지 않으면 재사용할 수 없다.
- 호환 가능하더라도 오래된 방식이면 그대로 승계하지 않는다.
- 기본 안전안은 회원 기본 정보만 이전하고 첫 로그인 때 이메일 확인 후 새 로그인 수단을 등록하여 기존 레코드와 연결하는 것이다.
- 이름 일치만으로 자동 연결하지 않는다. 동명이인과 사칭 위험이 있다.

### C. 로그인 연동과 안전한 이전이 모두 불가능한 경우

기존 회원 승계를 포기하고 새 회원가입을 받는 편이 안전하다. 공식 사이트 DB를 주기적으로 복사하거나 두 사이트가 같은 비밀번호 DB를 직접 공유하는 방식은 사용하지 않는다.

## 5. 상황별 Access의 위치

| 미래 상황 | 일반 사용자 인증 | 관리자 인증 |
|---|---|---|
| 현재 v1 | 회원가입 없음 | Access 유지 |
| 자체 회원가입 추가 | 앱 회원 인증 + D1 | Access 유지 권장 |
| 승인된 기존 회원 데이터 이전 | 앱 회원 인증 + D1 이전 데이터 | Access 유지 권장 |
| 교회 공식 OIDC/SAML 연동 | 공식 로그인 + D1 로컬 프로필 | 같은 인증원을 쓰더라도 Access 정책으로 관리자 제한 |
| 성숙한 통합 인증 완성 | 통합 회원 인증 | 아래 제거 조건을 모두 충족할 때만 Access 제거 검토 |

## 6. Access 제거를 검토할 수 있는 조건

다음이 모두 충족되어야 한다.

- 자체 또는 공식 회원 인증이 안정적으로 운영된다.
- 관리자 역할과 최소 권한이 서버에서 강제된다.
- 관리자 MFA가 적용된다.
- 관리자 API가 일반 회원 API와 확실히 분리된다.
- 관리자 계정 탈취 대응, 즉시 권한 회수, 세션 폐기 절차가 있다.
- 중요 관리자 조치가 변조하기 어려운 감사 기록에 남는다.
- migration·rollback 계획과 보안 테스트가 완료된다.

Access를 제거할 때도 D1이 Access를 대신하는 것이 아니다. 새 인증·인가 계층이 Access의 역할을 대체하고, D1은 그 계층이 사용하는 데이터 저장소 중 하나가 된다.

## 7. 실제 확장 시 다시 확인할 질문

1. 회원가입이 필요한 구체 기능과 예상 회원 수는 얼마인가?
2. 실명·교인 여부를 실제로 검증해야 하는가?
3. 공식 교회 사이트의 운영 주체가 연동 또는 데이터 이전을 승인했는가?
4. 공식 사이트는 OIDC, OAuth 2.0 또는 SAML을 지원하는가?
5. 외부 사용자 ID는 안정적이며 이메일 변경과 탈퇴를 처리할 수 있는가?
6. 이전 대상 필드·법적 근거·보존 및 삭제 책임은 무엇인가?
7. 관리자를 Access에 계속 분리할 것인가?
8. 당시의 Access 좌석 정책과 후보 인증 서비스의 무료 한도·비용은 얼마인가?
9. 계정 복구·MFA·탈퇴·정보 수정·세션 폐기를 누가 운영하는가?
10. 기존 참여 기록을 새 회원과 어떤 증거로 연결할 것인가?

## 8. 운영 매뉴얼에서의 위치

최종 운영 매뉴얼 구현 시 `/admin/manual`의 **나중에 확장할 기능** 항목에서 이 문서를 별도 페이지 `/admin/manual/future/member-auth`로 연결한다. 페이지에는 현재 적용 상태가 아니라 미래 검토 자료임을 눈에 띄게 표시하고, 실제 확장 결정이 내려지면 결정일·채택 구조·migration 계획을 덧붙인다.


## 9. 제품 안정화 이후 — 성경 문맥을 활용한 자막 고유명사 교정

2026-09-24 사용자 요청으로 기존 회원/계정 연동 기록과 함께 이 문서에 보관한다. **모든 계획된 개발을 끝내고 제품이 안정된 뒤 검토한다. 지금 구현하거나 P5-70의 필수 작업으로 추가하지 않는다.** 실제 재개 시점에 자료 취득 방식·허락 범위·비용·검증 기준을 다시 확인하고 구현 여부를 결정한다.

### 배경과 현재 구현

P5-70에서 사용자는 AI 교정안을 보고 “거의 완벽”하다고 평가했지만 일부 수정할 곳이 있다고 했다. 예로 ‘브닌나’가 ‘분인나’로 남은 고유명사 오인식을 들었다. 현재는 완벽한 퀴즈를 발행하는 단계가 아니라 시스템 동작을 확인하는 개발 단계이므로, 해당 교정안을 당장 다시 수정하거나 재생성하지 않기로 했다. 이 피드백은 실제 발행 품질의 최종 확정이나 DB 채택 완료를 뜻하지 않는다.

현재 [교정 전송 코드](../../workers/_shared/services/openai-draft-transport.ts)는 공통 지시문·교정용 지시문·자막을 함께 보낸다. 오타/띄어쓰기 교정, 의미·부정·숫자·성경 용어 보존, 창작/성경 본문 보완 금지, 구간 ID/순서/개수 보존을 지시한다. 다만 [교정 실행 입력](../../workers/_shared/services/content-generation.ts)은 자막만 포함하며, 등록된 설교 장절·판본을 별도 참고 자료로 전달하거나 성경 본문을 찾아 읽게 하는 기능은 없다. 자막에 장절이 언급돼 있다면 그 문맥을 읽을 수 있는 정도다. 이 설명은 기록 시점의 코드 기준이다.

### 향후 검토할 방향

- 설교의 장절·사용 판본을 교정 요청의 참고 정보로 함께 전달한다. 이것만으로 AI가 정확한 본문이나 표기를 조회·확인했다고 간주하지 않는다.
- **장절과 확인된 인명·지명 등 고유명사 목록**을 함께 제공하는 방식을 우선 검토한다. AI의 기억만으로 만든 목록을 검증된 정답으로 취급하지 않으며, 목록의 출처·확인 방법·판본별 표기 차이를 정해야 한다.
- 작업 지시와 참고 자료를 구분한다. 장절/고유명사는 자막의 표기 교정을 돕는 자료이며 설교 내용을 새로 작성하는 근거가 아니다. [OpenAI 공식 프롬프트 안내](https://developers.openai.com/api/docs/guides/prompt-engineering#message-formatting-with-markdown-and-xml)를 참고하되, 실제 도입 시 당시 API와 모델 기준을 재확인한다.
- 설교에는 다른 성경 인물, 현대 인물, 예화도 등장할 수 있다. 해당 장절의 인물/장소에 억지로 맞추거나 모든 유사 발음을 일괄 치환하지 않는다. 발음 유사성과 주변 문맥이 모두 맞는 경우에만 교정하고 불확실하면 원문을 유지한다.

지시문 예시(미적용 초안):

> 참고 고유명사는 표기 교정에만 사용한다. 자막의 발음과 주변 문맥이 해당 인물·장소를 가리킬 때만 교정한다. 확신하기 어려우면 원문을 유지한다. 참고 자료를 근거로 설교에 없는 내용을 추가하지 않는다.

### 먼저 생각해야 할 문제 — 성경 본문을 어떻게 가져올 것인가

**성경 본문을 어디에서 어떤 방식으로 가져올 수 있을지 별도로 조사·설계해야 한다. 아직 취득 경로나 사용 권한이 확보된 것으로 보지 않는다.** 다음을 함께 검토한다.

1. 공식 API, 허가받은 데이터 파일/제공 계약, 적법하게 이용 가능한 판본 등 어떤 출처를 사용할 수 있는가? 필요한 장절을 정확히 조회할 수 있고 판본·장절 대응과 갱신 이력을 확인할 수 있는가?
2. 본문 열람, 서버 저장·캐시, 외부 AI 제공자에게 전송, 고유명사 추출·활용, 사용자에게 공개하는 각 용도의 허락 범위는 무엇인가? 읽기 링크가 공개돼 있다는 사실만으로 수집·저장·AI 전송 허락을 가정하지 않는다. 수동 붙여넣기도 이 검토를 대신하지 않는다.
3. 본문 전문이 실제로 필요한가? 장절과 사람이 확인한 최소 고유명사 목록만으로 충분한지 비교한다. 목록을 만들기 위해 본문을 취득하는 경우에도 출처와 이용 조건을 확인한다.
4. 개역개정과 다른 판본의 명칭 차이를 어떻게 처리할 것인가? 다른 판본의 자료를 참고하더라도 목표 판본의 표기로 자동 확정하지 않는다.
5. 무료·저비용 방안, 데이터 이용료·API 호출료·운영 부담, 장애 시 장절/수동 참고 목록으로 돌아갈 방법은 무엇인가? 새 서비스나 유료 기능은 이유·대안·예상 비용을 제시한 뒤 결정한다.

현재 [성경 본문 정책](../spec/bible.md)을 유지한다. v1은 본문을 저장·복사하거나 AI로 생성·보완하지 않고 장절·판본명·공식 읽기 링크를 제공한다. 이번 기록은 성경 본문 취득·AI 전송 또는 정책 변경 승인이 아니다. 구체적인 취득 방법이나 허락 여부를 지금 확정하지 않는다.

### 재개 시 검증할 것

기존 교정 방식과 참고 자료를 추가한 방식을 같은 허락된 표본으로 비교한다. 고유명사 오인식 감소뿐 아니라 잘못된 자동 치환, 현대 인물/다른 성경 인물의 혼동, 의미·부정·숫자 변화, 내용 추가, 구간 ID/순서/시간 보존을 확인한다. 별도 유료 비교 실행 전에는 범위와 예상 비용을 정하고, 실제 최종 품질은 사람이 검수한다. 현재 교정안의 좋은 평가만으로 이 개선안의 효과가 검증된 것으로 기록하지 않는다.


## 10. 모든 구현 완료 후 — 두 난도의 영문 입력 알림 재확인

2026-10-03 사용자 요청. 어린이용·장년용에서 영문 입력 시 “영문이 입력됐어요. 한/영 키로 한글로 바꿔 주세요.”라는 알림을 4초간 표시하는 기능은 구현·자동 검사·Production 적용을 완료했다. 사용자는 지금 직접 확인할 수 없어 **모든 계획된 구현이 끝난 뒤 실제 화면에서 다시 확인하기로 했다.** 사용자 확인까지 완료됐다고 기록하지 않는다. 현재 P8-02 진행을 이 확인 때문에 멈추거나 같은 검사를 반복하지 않는다.

나중에 두 난도에서 영문 입력 시 알림이 눈에 잘 들어오는지, 한/영 전환 후 한글이 입력되는지, 기존 답안과 입력 초점이 유지되는지 확인한다. 현재 한글만 저장하는 정책은 유지하며 영문 허용 확대를 결정한 것은 아니다. 관리자 반복 테스트 방법을 마련할 때 아래 항목과 함께 검수한다.

## 11. 모든 구현 완료 후 — 관리자 반복 테스트 방법 검토

2026-10-03 사용자 요청. 현재 같은 브라우저 세션에서는 같은 주차의 어린이용·장년용을 각각 한 번만 제출할 수 있다. 운영자도 공개 풀이에서는 같은 정책을 적용받으므로 두 난도에 이미 제출한 뒤 다양한 입력·제출 상황을 다시 시험하기 어렵다. **관리자가 반복해서 테스트할 방법을 찾아야 한다는 후속 과제로 남긴다. 지금 기능이나 재참여 정책을 바꾸지 않는다.**

기존 관리자 기능·연습 경로·Preview를 재사용할 수 있는지 먼저 살피고, 필요하면 관리자 전용 시험 풀이 또는 별도 시험 문제를 비교한다. 실제 참가자의 성적·참여 현황·마감·동의 기록을 바꾸거나 시험 제출을 실제 순위에 섞지 않는 방법을 검토한다. 관리자 전용 경로를 택한다면 서버에서도 관리자 권한을 확인해야 한다. 구체 방식은 아직 확정하지 않았으며 새 계층·표·서비스를 추가하기로 한 결정이 아니다.

기존 제출을 삭제하거나 브라우저 정보를 지우는 일을 기본 해결 방법으로 안내하지 않는다. 시험 기록 초기화가 필요하다면 대상과 보존 범위를 먼저 정한다. 일반 참가자의 1회 제출 원칙은 유지하면서 운영자가 입력·알림·제출·채점·결과 재조회를 반복 확인할 수 있는지, 실제 운영 자료와 시험 결과를 구분할 수 있는지를 최종 검증한다.
