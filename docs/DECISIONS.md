# 주요 결정 기록

> 문서 역할: 앞으로 다시 논쟁하기 쉬운 선택과 그 이유를 짧게 보존한다.  
> 상세 동작과 예외는 루트 `implementation.md`를 따른다.  
> 마지막 확인: 2026-08-29, Asia/Seoul

## 기록 규칙

- 이미 적용된 결정을 조용히 삭제하거나 반대 의미로 고치지 않는다.
- 결정이 바뀌면 기존 항목을 `대체됨`으로 표시하고 새 항목에서 이유·영향·migration을 기록한다.
- 코드가 아직 결정을 구현하지 않았다는 이유로 결정을 폐기된 것으로 간주하지 않는다.
- 가격·정책처럼 바뀔 수 있는 사실은 확인일과 공식 출처를 함께 갱신한다.

## D-001 — 상세 명세는 루트 `implementation.md`에 유지

- 상태: 채택
- 결정: 34만 자 이상의 기존 `implementation.md`를 지금 이동하거나 여러 문서로 기계적으로 분할하지 않는다. 이 파일은 상세 제품·구현 명세 정본으로 유지한다. `PROJECT_CONTEXT`, `DECISIONS`, `STATUS`, `HANDOFF`는 탐색과 세션 복구를 위한 짧은 계층으로 추가한다.
- 이유: 기존 Git 기록과 README, 대화 인수인계가 모두 현재 경로를 가리킨다. 대규모 이동은 내용 개선 없이 링크와 기준만 흔들 수 있다. 반대로 한 파일에 상태·일지·규칙까지 계속 쌓으면 새 task가 필요한 정보를 찾기 어렵다.
- 영향: 새 task는 짧은 문서들을 먼저 읽고, 작업에 관련된 `implementation.md` 절을 추가로 읽는다. 전체 상세 명세를 요약 문서에 복제하지 않는다.

## D-002 — Cloudflare Workers + Static Assets 단일 웹앱

- 상태: 채택, 기존 Pages 계획을 대체
- 결정: Cloudflare Pages를 사용하지 않고, `biblequiz-app` Worker가 React Static Assets와 Hono `/api/*`를 함께 제공한다.
- 이유: SPA와 API, D1, Workflow binding, 보안 경계를 한 배포 단위에서 명시적으로 관리하기 쉽다. 현재 규모에서는 Workers Free 범위가 충분하다.
- 영향: 옛 문서나 코드에서 Pages Functions를 새로 만들지 않는다. 다른 호스팅으로 옮길 수 있도록 핵심 도메인 로직은 Cloudflare API와 분리한다.

## D-003 — D1 + Drizzle + 검토된 SQL migration

- 상태: 채택
- 결정: 제품 데이터는 D1에 저장하고 Drizzle을 type-safe query·schema 계층으로 사용한다. schema 변경은 생성된 SQL을 검토한 뒤 환경별로 적용한다.
- 이유: 예상 규모가 작고 Cloudflare Worker와의 결합이 단순하며 무료 범위가 넉넉하다. migration을 명시적으로 보존해야 AI 중심 운영에서도 변경 이력을 복구할 수 있다.
- 영향: `drizzle-kit push`를 사용하지 않는다. Production migration은 Preview 검증·백업·대상 확인·사용자 승인을 거친다.

## D-004 — Node 24와 pnpm 11 단일화

- 상태: 채택
- 결정: local, GitHub Actions, Workers Builds 모두 Node.js 24.18.0과 pnpm 11.14.0을 기준으로 사용한다. `pnpm-lock.yaml`만 유지한다.
- 이유: 환경별 차이와 AI가 다른 package manager를 섞어 쓰는 사고를 줄인다.
- 영향: npm·Yarn 설치 명령과 다른 lockfile은 금지한다. 버전 변경은 local·CI·Cloudflare를 함께 올리고 검사 후 문서를 갱신한다.

## D-005 — Preview와 Production을 물리적으로 분리

- 상태: 채택·Preview 적용 완료
- 결정: 현재 `main`은 Workers Builds를 통해 Access 보호 `biblequiz-app-preview`와 `biblequiz-d1-preview`에만 자동 배포한다. Production Worker·D1·도메인은 아직 만들지 않는다. 비기준 브랜치 자동 Preview build는 현재 끈다.
- 이유: 코드를 직접 검토하기 어려운 운영자가 실제 서비스 반영 전에 고정 Preview에서 확인할 수 있어야 한다. 현재는 하나의 개발 브랜치와 Preview 주소가 가장 단순하다.
- 영향: `main` push는 Preview 트래픽을 바꾸지만 Production 승인이 아니다. Pull Request별 임시 URL이 실제로 필요해질 때만 non-production branch build를 다시 검토한다.

## D-006 — 관리자 인증은 Cloudflare Access

- 상태: 채택·Preview 적용 완료
- 결정: v1 관리자 화면과 관리자 API는 Cloudflare Access의 `Cloudflare account / Allow`로 보호한다. 현재 Cloudflare 계정 구성원은 관리자 1명이고 세션은 6시간이다.
- 이유: 자체 회원·비밀번호 시스템 없이 관리자 경계를 만들 수 있고, 관리자 API가 공개 Worker 코드에 도달하기 전에 차단된다.
- 영향: 현재 계정에 다른 구성원을 초대하면 그 사람도 Preview 접근 대상이 되므로 정책을 재검토한다. 일반 회원가입이 생겨도 Access와 D1은 대체 관계가 아니며, 관리자 Access는 별도 제거 조건을 충족할 때까지 유지한다.

## D-007 — 일반 사용자는 회원가입 없이 익명 세션

- 상태: 채택
- 결정: v1 방문자는 회원가입하지 않는다. 서버가 발급한 브라우저 세션과 퀴즈·난이도별 제출 제약을 사용한다. 표시 입력 label은 설명을 덧붙이지 않은 `이름`이다.
- 이유: 교회 내부의 소규모 참여형 퀴즈에 회원 시스템의 운영·보안 부담이 과하다. 실명을 기술적으로 강제할 계획도 없다.
- 영향: 이름·답안·코멘트 공개·보관 동의를 받고, 문의·삭제 요청 폼과 접수번호 조회를 제공한다. 개인정보 공개 범위와 moderation은 회원가입 부재와 별도로 지킨다.

## D-008 — 성경은 개역개정 장절·판본·공식 링크만 표시

- 상태: 채택, v1 출시 게이트
- 결정: 비용을 지불하거나 별도 허가를 받지 않은 v1은 개역개정 본문 전문을 저장·복사·출력하지 않는다. 자연어 장절을 구조화하고 `개역개정` 표기와 대한성서공회 공식 읽기 링크를 제공한다.
- 이유: 관리자가 수동 복사해도 웹 공개·아카이브·인쇄 이용의 저작권 문제가 사라지지 않는다. 정확성도 AI 기억에 의존할 수 없다.
- 영향: 성경 본문을 AI가 생성·보완하지 않는다. 나중에 명시적 무료 허가 또는 적합한 라이선스가 확인될 때만 판본 레지스트리와 검수 절차를 거쳐 확장한다.

## D-009 — AI는 내용 이해, 코드는 퍼즐 배치

- 상태: 채택
- 결정: AI는 자막 교정 제안, 설교 의도·요약, 어린이용·장년용 정답 후보와 단서를 만든다. 관리자가 후보를 제외·수정·확정한 뒤, 결정론적 TypeScript 코드가 5×5~10×10 격자 크기·단어 조합·가로세로 위치·교차 밀도를 탐색한다.
- 이유: 설교 의도는 의미 판단이 필요하지만 격자 유효성·재현성·정답 비노출은 코드와 테스트가 더 정확하고 저렴하다.
- 영향: AI가 완성 격자 좌표를 최종 정답으로 결정하지 않는다. 배치기는 불가능한 조합에 이유를 반환하고 public grid와 private solution을 분리한다.

## D-010 — 설교 이해 품질을 AI 비용보다 우선

- 상태: 채택
- 결정: non-production에서 `gpt-5.6-terra`를 시작점으로 사용하되 설교 의도 분석과 별도의 비판 검토를 내부적으로 수행한다. 관리자 재생성 횟수와 입력·출력 token을 앱이 임의로 제한하지 않는다. 매주 누적 예상·실제 비용과 모델별 상세를 화면에 표시한다.
- 이유: 핵심 가치는 설교자의 의도를 정확히 파악한 요약과 문제 선정이다. 초기에는 관리자가 여러 초안을 비교할 가능성이 높다.
- 영향: 비용 표시와 사용자 승인 없는 모델 변경 방지는 필요하지만, 품질을 해치는 작은 token cap은 두지 않는다. Production 기본 모델 승격 전 실제 설교 품질·비용 평가가 필요하다.

## D-011 — 자막은 공개 CC 우선, 원본과 수정본을 보존

- 상태: 부분 채택·Production provider는 게이트
- 결정: 계정 연결 없이 공개 CC 데이터를 가져오는 adapter를 우선 시험한다. 성공한 원문은 불변으로 보존하고, 사람 직접 수정 후 바로 확정하거나 AI 오타 교정 제안과 diff를 검토한 뒤 사람이 최종 확정한다. 자막이 없거나 provider가 실패하면 텍스트 직접 붙여넣기를 무료 fallback으로 제공한다.
- 이유: 교회 YouTube 계정 권한과 자막 파일을 받을 수 없는 현재 운영 여건에서도 작업을 시작해야 하며, 발음 오류를 사람이 통제할 수 있어야 한다.
- 영향: 비공식 YouTube 음원 다운로드를 production 기능으로 만들지 않는다. 원본 음성 파일을 합법적으로 제공받는 별도 상황에서만 유료 AI 전사를 다시 검토한다.

## D-012 — 출력은 웹 데이터에서 재현하고 AI를 다시 호출하지 않음

- 상태: 채택
- 결정: 주보용 빈 격자는 PNG와 SVG, 단서는 복사 가능한 텍스트로 제공한다. Top N 벽보는 A4 세로 레이아웃을 브라우저 데이터로 렌더링하고 여러 페이지 PNG/PDF로 내보낸다. 사용자가 브라우저 머리글·바닥글 같은 복잡한 설정을 하지 않게 전용 출력 산출물을 제공한다.
- 이유: AI 생성 이미지에 텍스트를 넣으면 수정·검색·접근성·인쇄 품질이 나빠지고 매주 비용이 든다.
- 영향: 이미지 다운로드 시 AI를 다시 호출하거나 임의 화면 캡처에 의존하지 않는다. 빈 문제 자료와 Top N 출력의 접근 조건은 서로 다르다.

## D-013 — 정적 이미지는 Git, R2는 비공개 백업만

- 상태: 채택
- 결정: 어린이·장년 배경과 축하 요소는 최적화한 AVIF/WebP 정적 자산으로 Git에 두고 Workers Static Assets로 제공한다. R2는 공개 이미지 서버가 아니라 D1 주간 SQL 백업 정상본 8개 순환에만 사용한다. KV는 v1에서 사용하지 않는다.
- 이유: 현재 자산·트래픽 규모에서는 별도 이미지 저장소가 필요 없고, 서비스 수와 과금 위험을 줄일 수 있다. DB 백업은 앱 배포와 분리된 비공개 저장소 가치가 있다.
- 영향: 자산이 실제로 커질 때 사용량을 측정한 뒤 R2 공개 자산 전환을 재검토한다. R2 활성화 전 요금과 결제 등록을 다시 안내한다.

## D-014 — 디자인은 시안 승인 뒤 구현

- 상태: 채택
- 결정: Phase 2 순수 퍼즐 엔진까지는 디자인 없이 진행한다. Phase 7A에서 `imagegen-frontend-web` 시안을 만들고, 이후 실제 화면은 `design-taste-frontend`, 별도 모바일 세로 이미지는 `imagegen-frontend-mobile`을 사용한다.
- 이유: 데이터 구조와 퍼즐 규칙을 먼저 안정화하면서도 실제 공개 UI가 임시 scaffold 디자인에 끌려가지 않게 한다.
- 영향: 현재 임시 화면을 최종 디자인으로 다듬지 않는다. 라이트는 Everforest, 다크는 Gruvbox 방향을 유지한다.
