서버 진입점은 `workers/app/weekly-routes.ts`, `workers/_shared/services/admin-weekly.ts`·`privacy-requests.ts`, `workers/app/app.ts`의 기존 Access 뒤 mount다. 새 middleware는 새 endpoint에만 적용해 기존 공개/생성 query를 차단하지 않는다. 전체 자막·정답·관리자 신원은 첫 화면 집계에 넣지 않는다. 삭제된 제출은 점수/묘비만 남기며 새 조치 서비스나 재채점을 만들지 않았다. 공개 제출 수는 활성·유효한 문제만 집계하며, 오류로 무효화된 이전 문제의 제출은 전체 이력 수에 보존한다.

최초 자료 등록·설교 정보 사람 확인·확정·AI 실행·발행은 명시적 버튼이다. 자동 저장으로 이 동작을 실행하지 않는다. 기존 D1 결과/원문/키/유료 결과를 그대로 사용한다. 서비스 전체 metric/백업·공개 요청 제한의 운영 설정·문의 보존 기간과 정리 Cron은 기존 P8-01 범위이며 이 작업에서 임의 값을 정하거나 준비 완료로 표시하지 않았다.

## 0037과 원격 승인 경계

0037은 명세에 필요한 `privacy_requests`와 조회 hash unique/status-time 인덱스만 추가한다. Drizzle schema 수정 → SQL/snapshot 생성 → CREATE만 있는 SQL 검토를 수행했다. 0000~0036 SQL/snapshot은 변경하지 않았다. 기존 site_state·필터·제출·감사 표를 재사용하므로 새 설정/편집 표는 없다. 임시 검사 DB에만 migration을 적용했으며 root DB·P5-70 실제 DB·Preview에는 적용하지 않았다.

조회키는 기존 SESSION_PEPPER와 requestKey의 HMAC에서 복구하는 PRV+256-bit 값이다. D1은 조회키 SHA-256·내용 hash만 보관한다. 브라우저 성공 접수번호는 기존 저장 접근 helper를 통해 localStorage에 둔다. 관리자 답변 API에는 expectedUpdatedAt·감사가 있고 공개 조회는 종류/시각/상태/답변만 반환한다. 문의의 처리 완료는 실제 제출 삭제를 자동 실행하지 않는다.

새 기능을 Preview에 반영하려면 **별도 구체적 승인**이 필요하다. 승인 범위는 기존 Preview D1 목록/대상 확인·보존 사본 → 0037 한 개 적용 → 검사한 앱 Preview 배포 → 합성 운영 화면/권한/응답과 자료 보존 검수다. Production·실제 자료 변경·기존 유료 결과 재생성·유료 플랜 전환은 포함하지 않는다. 승인 없이 이 절을 실행 지시로 사용하지 않는다. 로컬 검사 성공은 새 원격 CPU/현재 사용량 검수 성공을 뜻하지 않는다.

## 폐기한 접근과 남은 경계

WSL 경로를 다시 연결해야 한다는 초기 설명은 실제 원인이 아니었다. 경로와 저장소는 이미 설정돼 있었으며 명령 실행 방식 문제를 확인해 처리했다. 사용자에게 환경 재설정이나 원문/키 재입력을 요구하지 않는다.

한 내용 저장 뒤 전체 editor를 버전 key로 재생성하는 접근은 다른 편집본을 잃을 수 있어 주간 화면에서 쓰지 않는다. snapshot ID를 기준으로 편집본을 유지하고 저장/선택 상태를 대조한다. 실패한 저장의 무한 자동 재시도·페이지 진입 시 AI 실행·원격 승인을 과거 승인으로 대신하는 접근도 사용하지 않는다.

다음은 **P6-01 빈 격자·단서·Top N 출력 전체**다. 새 관리자 Preview 적용은 승인 전 미실행 상태로 유지한다. 문서화된 P5-72 로컬 범위의 미완료 코드/검사는 없으며 공개 요청 제한/Cron·서비스 metric/백업·실기기는 기존 후속 범위에 남아 있다.
