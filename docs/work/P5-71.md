## 반복 조회 수정과 제한 검사

[읽기 세션](../../workers/_shared/repositories/generation-read-session.ts)은 요청/실행 구간 안의 검증된 불변 자료만 재사용하고 독립 SELECT를 batch로 묶는다. 현재 선택·metadata·head·정리 여부·품질은 새로 읽는다. 쓰기/외부 호출 전후에는 캐시를 해제하고, 같은 불변 읽기의 진행 중 작업도 공유한다. 캐시 크기는 전체 BLOB/JSON 재직렬화 없이 보수적으로 계산하며 4MiB 경계를 유지한다.

[문맥 codec](../../workers/_shared/services/generation-context-codec.ts)은 이미 확인한 chunk/전체 해시를 다시 생성하지 않으며 정본 형식·schema·출처·참조·guidance 검사는 유지한다. [UTF-8 길이](../../workers/_shared/storage/utf8-byte-length.ts)와 [D1 hex 전송](../../workers/_shared/storage/d1-hex-blob.ts)은 반복 배열 생성과 숫자 배열 JSON 비용을 줄인다. 저장 BLOB/원본은 바꾸지 않으며 chunk 길이·순서·SHA·UTF-8 손상 검사는 유지한다. Drizzle query builder만 재사용하며 DB 행을 전역 캐시하지 않는다.

[최종 완료](../../workers/_shared/services/content-generation-final.ts)는 현재 입력·내용·사람 검수·비용·metadata·정리·품질을 검증하고 기존 proof/작업 상태를 한 조건부 거래로 기록한다. 부분 UPDATE 실패 rollback·마지막 시점 변경·응답 유실 복구 검사를 유지했다. 자료 길이/후보 수나 검증 수준을 줄이지 않았다.

로컬 완료 SQL263→248/RPC48 개선은 원격 CPU와 별개다. Node 비교의 CPU 감소나 로컬 50회 모사는 원격 성공의 대체 근거가 아니다. 실패를 다시 실행하기 전에 재현된 병목의 코드 변경과 전체 검사를 완료했다.

## 관리자 표시 읽기 수정

[표시 전용 읽기](../../workers/_shared/services/content-generation-display.ts)는 현재 선택/이력과 필요한 의존 결과만 읽는다. 기존 SHA·byte·chunk·UTF-8 검증, 소유자/AI 성공 결과 연결·human operation·현재 head 재확인을 유지하고, 발행을 허용하는 DomainBasis/read witness는 만들지 않는다. 입력 교체 후 옛 결과를 비교하는 동작도 유지한다. snapshot은 content_sequence 순으로 정렬해 이전 화면 순서와 일치한다.

[화면 조회](../../workers/_shared/services/content-generation-view.ts)는 독립 SELECT를 batch로 묶고, metadata/선택 ticket/품질을 확인한 뒤 [표시 계산](../../workers/_shared/services/generation-final-validation.ts)을 호출한다. GET마다 전체 발행 검증을 재실행하지 않는다. 실제 완료·발행은 기존 `validateCurrentGenerationFinal`의 전체 검증을 계속 사용한다. Drizzle 관계 등록은 실제 관계 조회를 쓰는 sermons/siteState로 한정했고, 런타임 current row schema는 요청마다 다시 만들지 않는다. 실제 DB 행의 전역 캐시는 추가하지 않았다.

변경 전 원격 응답과 최신 로컬 소스 응답은 세 시험 모두 **전체 필드와 배열 순서까지 동일**하다. Node/workerd 사본 프로파일에서 여러 D1 읽기/응답 처리, schema 초기화와 결과 재계산 비용을 확인했지만 이를 원격 CPU 감소율로 쓰지 않는다. 두 번째 배포 뒤에도 10ms 미달이므로 현재 수정만으로 문제를 해결했다고 하지 않는다. 이전 표시 읽기 수정 시점에는 요청별 분할·표시 사전 저장을 검토만 했다. 아래 후속 구현에서 HTTP 분할을 연결했고, 표시 사전 저장·새 표/0036은 추가하지 않았다. 같은 구조의 미세 수정·변경 없는 재배포로 통과를 기대하는 접근은 반복하지 않는다.

## Cloudflare 내부 최종 검사

[Workflow](../../workers/content/index.ts)의 `final-check` 경로가 기존 전체 완료 검증/원자 저장을 실행한다. 새 생성 작업·DB 표·외부 서비스는 만들지 않았다. [요청 계약](../../shared/api/admin-content-final-check.ts)·[Workflow 접수/상태](../../workers/_shared/services/content-final-check-workflow.ts)는 같은 requestKey를 같은 final instance에 연결한다. 실패/불확실한 실행을 자동 재시작하지 않는다.

POST finish는 202를 반환하고 Access 보호 GET으로 작은 진행 상태만 조회한다. [기존 관리자 화면](../../src/features/admin-sermon-input/ContentGeneration.tsx)은 완료 대기 중 중복 누름을 막고, 같은 키를 유지하며 최대 1분 상태를 확인한다. 원문/초안 그래프는 D1에 남고 공개 응답이나 Workflow 출력에 넣지 않는다. 최종 성공 뒤 원래 생성 Workflow에도 완료 알림을 보낸다.

`CONTENT_FINAL_CHECK_WORKFLOW_ENABLED`는 기본 false다. Preview에서는 origin/최대 세 자료 UUID 허용 목록과 합성 원문 검사를 통과해야 실행했다. 시험 후 false로 되돌렸다. 기존 로컬 P5-70 완료 경로와 발행/공개 풀이 동작은 유지했다.
