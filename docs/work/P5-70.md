적용 직전 DB 작성 프로세스 종료·계획/코드/SQL/DB 지문 일치를 확인한다. 실패 시 적용 트랜잭션 전체를 취소하고 결과가 불명확하면 같은 receipt부터 읽는다. 후속 결과 오류는 새 호출/확정/발행을 멈추고 원응답/비용을 대조한다. 자동 사본 복원이나 원래 이력 삭제를 하지 않는다.

## 재사용 가능한 빈 로컬 준비 도구

[prepare-ai-quality-trial.mjs](../../scripts/prepare-ai-quality-trial.mjs)를 추가했다. 프로젝트 루트에서 다음 명령을 사용한다.

```sh
pnpm exec node scripts/prepare-ai-quality-trial.mjs
```

이 명령은 실제 AI 시험 실행기가 아니다. 현재는 매번 새로운 비공개 영속 디렉터리를 만들고 다음만 수행한다.

1. 기존 `wrangler.generation-local.jsonc`에서 DB/Workflow 구성을 읽고, 고유 임시 config와 상태 디렉터리를 만든다. 기존 config와 `.wrangler/state`는 변경하지 않는다.
2. 기존 0000~0029를 **새 빈 로컬 DB에만** 적용한다. 기존/원격 DB의 migration을 적용하는 명령이 아니다. 자료 seed·새 migration은 없다.
3. AI/초안 정리를 false로 고정하고 가짜 Access 식별자만 넣는다. 별도 빈 `.dev.vars`와 `.env`를 생성하며 부모 환경의 API 키를 전달하지 않는다. 원본 설정의 추가 변수도 복사하지 않는다.
4. 원격 binding을 끈 `--local`, loopback `127.0.0.1`, 별도 `--persist-to`로 잠깐 서버를 실행한다. health/DB 조회와 인증 없는 관리자 GET/생성 POST의 거부를 확인한다. JWT를 만들어 인증을 우회하지 않는다.
5. 서버를 종료하고 임시 config·빈 DB·`preparation.json`·준비 로그를 남긴다. 콘솔에는 원문/비밀값 없이 경로·검사 결과·남은 조건만 표시한다. 인자를 받지 않으므로 이 도구에 `--remote`, 키, 원문을 넘겨 유료 실행기로 바꿀 수 없다.

Node 24.18.0·pnpm 11.14.0·설치된 Wrangler 4.125.0으로 검증했다. `.mjs` 개발 보조 도구이며 앱/API/화면·schema·모델·가격표를 수정하지 않는다. 원격 계정의 플랜/현재 설정/청구액은 확인하지 않았다.

## 실제 시험까지 남은 로컬 연결

현재 앱의 Access 검증은 HTTPS의 Cloudflare Access issuer와 서명된 JWT를 요구한다. 가짜 식별자만 넣은 위 준비 환경은 사람이 로그인해 실자료를 검수할 수 있는 환경이 아니다. 빈 준비 도구만으로 실호출 가능하다고 표시하지 않는다. 추가한 로컬 세션 도구와 실제 인증 연결의 남은 조건은 아래를 따른다. 기존 [Workflow 합성 테스트](../../workers/app/content-workflow.test.ts)는 테스트 안에서 JWKS·AI 응답을 주입하며, 실제 키와 실제 자료를 넣는 장기 검수 실행기가 아니다.

같은 P5-70에서 확보한 자막을 바탕으로 다음을 마쳐야 유료 실행 승인을 요청할 수 있다.

- 자료 종류·문자 수·시간 정보·SHA 확인은 완료했다. 실제 내용의 정확성·영상 전체/부분 coverage와 기준답·예상 요청 구조는 남아 있다. 원문/키를 Git·로그에 복사하지 않는다. 입력 한도에 맞추기 위한 자르기·요약은 하지 않았다.
- 기존 API/Workflow를 사용하는 로컬 세션 도구와 합성 검증을 완료했다. 실제 Access 설정·정상 토큰으로 인증된 빈 세션 연결은 아래 후속 검사에서 완료했다. 제품의 Access 검사를 끄거나 공개 무인증 실행 route를 만들지 않는다.
- 실제 모델/high·교정 포함 여부·자료 한 편·호출 묶음·예상액·중지 방법이 모두 정해진 뒤 구체 실행 승인을 받는다. 첫 1편의 비용 가정과 USD 2 검토 기준은 [P5-69 비용안](P5-69.md#예상-비용과-대안)을 재사용한다. 아직 측정한 자막 토큰량이 없으므로 새 확정 견적을 만들지 않는다.

이번에는 사용자의 후속 자동 추출 요청에 따라 자막을 확보했으므로 붙여넣기를 다시 요구하지 않는다. 자막 취득·분량 확인 승인은 유료 AI 전송·기존 DB 등록 승인으로 확대하지 않는다.

## 사람이 검수할 로컬 세션 도구

[local-ai-quality-session.mjs](../../scripts/local-ai-quality-session.mjs)는 기존 앱/API와 Content Workflow를 별도 빈 로컬 D1에서 실행한다. 새 화면·인증 방식·제품 API·migration을 추가하지 않았다. 이후 추가한 저장 자막 등록 경로는 아래의 로컬 전용 진입점에만 존재한다. 브라우저 로그인 UI가 아니라 운영자가 비공개 요청/응답 파일로 기존 API를 사용하도록 돕는 개발 도구다. 기존 Access 서명·issuer·audience·만료 검사는 그대로 유지한다. 도구 추가 당시 실제 인증 성공은 미확인이었고, 아래 후속 검사에서 정상 사용자 JWT로 빈 목록 조회를 확인했다.

- 시작 시 명시적으로 지정한 0600 설정 파일만 읽는다. 기존 `.env`/`.dev.vars`와 부모의 AI 키/Cloudflare 환경 변수는 읽거나 전달하지 않는다.
- 현재는 매번 `~/.local/state/biblequiz/quality-session-*` 0700 디렉터리와 새 D1을 만들고 0000~0029만 적용한다. loopback·`--local`·고유 `--persist-to`를 사용하며 서버는 검수 중 계속 실행된다.
- 기본 AI 비활성·정리 비활성이다. `paidExecutionApproved: true`와 명시적 비공개 키 파일이 모두 있어야 유료 연결 설정이 가능하다. 이 설정 기능의 구현은 실행 승인이 아니다. 이번 검증에서는 false·키 없음만 사용했다.

## 로그인 전달 진단과 실제 연결 완료

후속 읽기 전용 진단에서 앞서 관측한 Python GET 403은 Cloudflare **1010**임을 확인했다. 같은 URL에 공식 CLI 식별자를 사용하면 Access metadata와 정상 로그인 302→302→200이 반환된다. 이는 클라이언트 식별에 따른 차단 증거이며 Preview 장애·관리자 권한 오류로 단정할 수 없다. 보안 설정은 변경하지 않았다. [1010 공식 설명](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/).

공식 [전달 소스](https://github.com/cloudflare/cloudflared/blob/2026.9.1/token/transfer.go)를 대조했다. `/cdn-cgi/access/cli`에서 앱 루트로 `isCLI`와 교환용 공개키를 넘기는 302는 실제 정상 중간 단계다. 주소의 `token`은 API 인증 JWT가 아니며 이를 인증 헤더로 사용하지 않는다. 사용자는 앱 내 브라우저와 새 기본 브라우저 모두 최종 화면이 성경 퀴즈 앱 첫 화면이라고 확인했다. 활성 CLI로 기본 브라우저 연결을 한 번 새로 시도했으나 공식 `access token --app`은 exit 1·JWT 없음이었다. 원인은 아직 확정하지 못했으며 대기 프로세스는 종료했다. 동일 로그인 반복·정책 변경·추가 서비스 생성은 하지 않는다.

정확한 Preview의 공개 metadata JWT를 HTTPS HEAD로 취득해 RS256 서명·hostname·type·발급 시각을 검증했다. 해당 공개 JWKS를 사용했으며 사용자 토큰에서 임의로 대상 값을 정하지 않았다. 비공개 `/tmp/p5-70-access-tools/settings.json`은 그 결과로 만든 실제 team domain/audience·`paidExecutionApproved: false` 설정이다. 이는 **앱 대상 확인 성공**이며 사용자 로그인 검증 성공은 아니다. 원문·키·이메일·JWT를 Git/출력에 기록하지 않았다.

남은 사용자 동작은 로그인된 Preview의 `CF_Authorization`을 비공개 로컬 파일에 직접 전달하는 것이다. Chrome/Edge F12 → Application → Cookies → Preview 주소에서 해당 값만 복사한 뒤 WSL에서 다음을 실행하고 숨김 입력에 붙여넣는다. 항목이 없으면 다른 cookie를 임의로 가져오지 않고 중단한다. 입력값을 대화·명령 인자에 넣지 않는다.

```sh
python3 /tmp/p5-70-access-tools/receive-browser-token.py
```

0030은 Drizzle schema 수정 후 generate로 생성하고 SQL을 검토했다. 일반 생성/human 저장 guard를 보존하면서 일치하는 복구 event에만 진입을 허용한다. receipt와 event의 deferred FK/기존 봉인 규칙으로 한쪽만 저장하지 못한다. batch 안에서 현재 입력/콘텐츠 head, metadata/selection revision, 미발행/cleanup/다른 활성 job과 원래 실패/정산 상태를 검사한다. 최초 단일 SQL assertion은 D1 expression depth 100에 걸려 독립 assertion들로 나눴다. 검사를 삭제하거나 한도를 높이지 않았다. 실제 DB에는 0030을 적용하지 않았다.

### 검증 범위와 현재 한계

합성 fixture는 해당 job에만 이전 domain 거절을 주입하고 원래 사용량을 남긴다. 저장·기존 앱 콘텐츠 조회·같은 요청 반복·다른 actor/바뀐 원문 거절·출처 update/delete 차단·사람 확정 차단을 검증한다. 저장 후에도 원래 상태 failed/분석만 존재/critique·confirmation null이며 기존 비용 560 micro-USD(합성)의 행 값이 그대로다. 마지막 저장 단계의 강제 실패는 receipt/event/head/payload/chunks/lineage 모두 rollback되고 무료 재시도가 가능하다. 마지막 읽기 이후 metadata revision이 바뀌어도 SQL에서 거절한다. receipt만 저장하는 별도 진단에서도 deferred FK 거절을 확인했다. 이 진단은 workerd의 D1 actor 재시작을 유발하여 공유 Worker 회귀에서는 제외했고, 원자 rollback은 마지막 단계 실패를 주입한 유지 회귀로 검증한다.

초기 병렬 검사에서 시험용 abort trigger가 다른 설교에도 적용되고 전역 행 개수를 비교해 간섭했다. trigger·거절 주입·보존 비교·count를 각 fixture의 sermon/job 범위로 좁혔다. 실제 자료와 무관한 합성 격리 문제였으며 제품의 실패 처리를 성공으로 바꾸지 않았다. 이후 직렬 회귀에서 91/92 통과와 사용량 기록 단계의 간헐 실패 1건이 남았다. 별도 재검사 3개는 통과했지만 그것만으로 해결로 간주하지 않았다. 반복 합성 진단에서 실행 시간이 -161ms로 표시되면서 `generation_jobs_time_check` 거절이 두 번 발생해 시험 중 시간 역행을 확인했다. `content-intent-generation.test.ts` 및 복구 준비/저장 시험에서 각 시험의 Date만 고정하고 종료 시 복구하도록 했으며, 실제 타이머/명시 날짜/SQL 시간 검증 규칙은 유지했다. 진단용 로그와 반복 시험은 제거했다. 관련 기존 생성/domain 흐름과 필수 lint/typecheck/db:check 및 최종 결과는 검증 JSON `recovery_storage`와 HANDOFF를 따른다.

**실제 영속 DB 적용은 미실행**이다. 개인 준비 package/검수 HTML/키/자막/실제 응답/비용은 그대로다. 직전 package의 `appRecoveryCommitImplemented=false`는 당시 준비 시점 기록으로 보존하며, 새 코드로 준비할 때는 true다. 이 flag가 writePermit/사람 승인/실제 적용 완료를 의미하지 않는다. 새 store는 내부 함수로만 제공되며 공개/원격 route나 자동 Workflow에 연결하지 않았다. 기존 앱 조회 경로가 합성 복구 내용을 읽는 것은 확인했지만 실제 사용자 브라우저에서 앱 반영 검수는 하지 않았다.

### 다음 작업과 적용·rollback 조건

같은 P5-70에서 실제 영속 시험 DB 적용을 구체적으로 준비한다. 같은 DB/원래 source job/확정 version 4/보관 파일 지문/현재 비용을 확인하고 0030 대상·복구 event를 고정해야 한다. 실제 자료 쓰기는 사용자가 승인한 적용 범위에서만 수행하고 새 DB 생성·입력 재등록·유료 분석 재호출을 하지 않는다. 적용 시 실패하면 D1 batch가 복구 기록/콘텐츠를 함께 취소하고 기존 failed/usage는 유지한다. 결과가 불명확하면 동일 event 출처/본문을 조회해 판정하며 원래 실패 job을 다시 보내지 않는다. 적용 후 이상이 발견되면 후속 호출/확정/발행을 멈추고 보존된 출처로 진단한다. DB 사본 복원이나 복구 행 삭제로 과금/실패 이력을 지우지 않는다.

복구 저장 후에도 비판은 아직 실행되지 않았다. 현재 retryCritiqueOnly는 성공 분석이 있는 intent v2 전용이므로, 복구된 full v3 분석으로 **분석을 재호출하지 않고 비판만 이어갈 명시 경로**는 남아 있다. 실제 적용과 그 연결/추가 유료 승인·사람 확정은 구별한다. 이번 새 테이블·helper는 기존 제한을 우회해 failed를 검수 대기로 위장하지 않는다. 기존 결과와 키 재사용, 고유명사 개선 보류, P5-70/Phase 5 진행 중·세션 유지 기준은 그대로다.

### 도구와 실행 경계

`node scripts/apply-archived-intent-recovery.mjs plan <기존 manifest 절대 경로> <새 개인 출력 폴더>`는 실제 SQLite를 readOnly로 연다. 기존 `prepareArchivedIntentRecovery`로 원래 request/response·실패/정산·현재 문맥을 검사하고, DB 전체의 논리 지문·보관 지문·실행 코드 지문·0000~0030 SQL 지문·적용 event ID를 고정한 `application-plan.json`과 `review.txt`를 만든다. 기존 준비 package/교정안/검수 HTML을 덮어쓰지 않는다. 파일 내용은 개인 폴더에만 있고 stdout에는 검사 요약만 나온다.

`apply <계획 절대 경로> <확인한 계획 SHA256>`은 별도로 승인한 로컬 적용용 명령이다. 같은 OS 운영자, 같은 코드/SQL/자료/DB인지 재검사하며 원래 DB가 있는 영속 개인 경로만 연다. 키나 Cloudflare 로그인을 사용하지 않고 외부 fetch를 차단한다. 적용 actor는 OS 사용자 ID와 home 경로를 namespace와 함께 해시한 `local_os_operator`이며 Cloudflare 재인증을 했다고 기록하지 않는다. 계획 지문 입력은 도구의 실수 방지 조건이며 사용자 승인을 도구가 대신 판단하지 않는다.

적용 전에는 이 DB를 사용하는 앱/Worker/보관기를 종료한다. SQLite backup API로 새 비공개 사본을 만들고 파일/디렉터리를 fsync한 뒤 사본의 논리 지문을 확인한다. `BEGIN IMMEDIATE`로 쓰기 잠금을 얻은 뒤 실제 DB 지문을 다시 대조한다. **0030 SQL·migration 이력 1행·기존 복구 service의 저장을 하나의 외부 트랜잭션으로 묶는다.** Node SQLite의 D1 adapter는 내부 batch를 SAVEPOINT로 연결한다. 정상 봉인과 quick_check/FK, 변경 허용 콘텐츠 표 이외의 모든 기존 표/이력 지문이 일치해야 commit한다. 기존 job/outcome/call/usage/input·다른 원래 이력은 바꾸지 않는다.

마지막 저장이 실패하면 새 테이블/trigger/migration 이력/복구 콘텐츠가 모두 rollback된다. 이미 적용된 같은 출처는 실제 불변 기록을 검증하고 `replayed`로 반환한다. 성공 뒤 보고서 쓰기만 실패한 경우에도 원래 AI를 재전송하거나 DB를 자동 복원하지 않는다. 다음 동일 계획 실행에서 receipt로 성공 여부를 확인한다. 적용 후 내용이 이상하면 후속 호출/확정/발행을 중단하고 분석/출처를 대조한다. 복구 기록 삭제나 무조건 사본 복원으로 과금 이력을 지우지 않는다.
