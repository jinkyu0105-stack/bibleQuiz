# P8-02 배치 원인 조사와 출시 마무리 준비

2026-10-05. 사용자 요청 범위는 원인·수정안 설명, 백업/비용 미확인 항목 점검, 향후 UI 계획 기록이다. 제품 코드 수정·유료 재생성·발행본 교체·배포·main push는 하지 않는다. 현재 P8-02/Phase8은 마무리 준비 중이며 완료 선언은 하지 않는다.

## 1. 원하는 문제 수가 안 나온 이유

**문제 수 자체가 불가능했던 것은 아니다. 같은 후보로 어린이8×8/5개, 장년9×9/6개가 성공했다.** 이전 안내는7×7까지만 시험하고3개로 줄이도록 권해 더 큰 격자의 무료 대안을 놓쳤다. 이미 발행한3개 시험지는 그대로 보존한다.

| 실제 저장 후보 | 어린이 | 장년 |
|---|---:|---:|
| 후보 수 | 16 | 15 |
| 5글자 이하 | 13 | 12 |
| 6글자(5×5에서 제외) | 3 | 3 |
| 5글자 이하 중 서로 연결 가능한 최대 묶음 | 4 | 4 |
| 기본 목표 | 5 | 6 |
| 잠금·제외 후보 | 0 | 0 |

퍼즐은 같은 완성형 한글 글자로 모든 답이 연결돼야 한다.5×5에서는6글자 후보가 빠지고 남은 후보의 최대 연결 묶음이4개라5개/6개를 넣을 수 없다. 후보 총수가 모자라거나 잠금 상태가 잘못된 문제가 아니다. 연결 가능4개도 공간/인접 제한 때문에 반드시 배치되는 것은 아니다.

코드 근거:
- [AI 입력](../../../workers/_shared/services/ai-draft-provider-contract.ts): 자막·확정 의도, 선택적 한 문제 교체 정보만 받는다. 최초 요청에 저장한 격자/목표 개수가 후보 AI 입력으로 전달되지 않는다.
- [실제 지시문](../../../workers/_shared/services/openai-draft-transport.ts): 난도별 명사/명사구 약15개·근거·단서를 요구하나 선택 격자에 맞는 길이와 연결 가능한 조합은 지시하지 않는다.
- [후보 탐색](../../../shared/puzzle/pool-search.ts): 격자보다 긴 후보를 제외하고 연결 묶음이 목표보다 작으면 DISCONNECTED_CANDIDATES를 반환한다. 현재 오류는 이 사전 검사에서 재현됐다.
- [화면](../../../src/features/admin-sermon-input/ContentPlacement.tsx): 실패 이유를 일반 문장으로 보여주며 가능한 크기/개수는 운영자가 직접 시험해야 한다.

### 같은 자료·운영 옵션으로 한 추가 오프라인 시험

실제 선택 후보·동일 정렬·저장된 seed/탐색 예산으로 기존 순수 TypeScript 엔진을 실행했다. 단어를 수정하거나 AI를 호출하지 않았다.

| 목표 | 5×5 | 6×6 | 7×7 | 8×8 | 9×9 | 10×10 |
|---|---|---|---|---|---|---|
| 어린이5개 | 연결성 실패 | 배치 못 찾음 | 배치 못 찾음 | **성공2안** | 성공3안 | 성공3안 |
| 장년6개 | 연결성 실패 | 배치 못 찾음 | 배치 못 찾음 | 배치 못 찾음 | **성공2안** | 성공3안 |

시험은 탐색 예산 미완료 표시 없이 끝났다.5×5 연결 묶음 부족은 구조적 불가능이며, 다른 크기의 탐색 실패를 모든 알고리즘에서의 수학적 불가능으로 확대하지 않는다. 새 크기의 결과는 로컬 재현이며 운영 발행본에 적용하지 않았다. 기존5×5/3개와7×7/4개 성공 증거도 보존한다.

### 수정안 — 아직 구현하지 않음

1. **즉시 가능한 무료 경로:** 기존 UI에서 어린이8×8/5개·장년9×9/6개로 시험할 수 있다. 발행 후 수정은 제출 유무에 따른 기존 revision/교체 절차를 따르며 이번 조사에서 적용하지 않는다.
2. **우선 권장하는 프로그램 개선:** 기존 배치 엔진으로 허용 크기별 대안을 계산해 ‘5×5에서는 연결 후보 최대4개,8×8이면5개 가능’처럼 제시한다. 운영자가 선택하기 전에 격자·목표를 자동 변경하지 않는다. 새 서비스/AI 비용은 필요 없다.
3. **후보 품질 개선:** 선택한 크기·목표 수·허용 길이·공통 글자 연결 조건을 기존 후보 AI 입력에 전달하고, 생성 직후 기존 엔진으로 무료 사전 배치를 검사한다. 실패해도 결과/비용을 보존하고 부족한 연결 후보를 설명한다. 필요한 후보만 명시적으로 교체하는 기존 기능을 재사용한다. 프롬프트만으로 성공을 보장하거나 자동 유료 재시도를 도입하지 않는다. 원문에 없는 답·명사구 임의 절단은 하지 않는다.

명세4.1에서5×5의5~6개/6~8개는 추천값이며 고정 보장은 아니다. 따라서 문제 수 축소를 유일한 해법으로 설명한 안내를 정정하되, 새 엔진이나 고정5×5 보장 요구를 임의로 추가하지 않는다.

## 2. 예약 백업은 무엇이고 실제로 실행됐는가

운영 D1의 schema+data를 SQL gzip 파일로 내보내 비공개 R2에 보관한다. 설교·자막/생성 자료·퀴즈·제출·운영/비용 원장 등 **DB 자료**의 복구용 사본이다. Git 소스·로컬 비밀키·Worker 설정 전체를 대신 백업하는 기능은 아니다.

- 주간 SQL: 월요일04:00 KST(일요일19:00 UTC). 최신 정상 주간본8개 순환. 수동/변경 전 사본은 별도이며 주간 순환으로 자동 삭제하지 않는다.
- 삭제 목록:10분마다 별도 동기화. 삭제된 제출이 오래된 SQL 복원 때 되살아나지 않도록 식별 표식을 남긴다. 백업 복원 시 재적용한다.
- **첫 실제 주간 실행:**2026-10-05 04:00:28 시작 →04:00:41 완료,517,648bytes,verified. 코드상 저장한 파일의 전체 크기·SHA를 다시 읽어 대조한 뒤 verified를 기록한다.
- 최신 확인 삭제 목록:2026-10-05 12:00:28 시작 →12:00:30 완료,verified.10월4일 이후 failed/queued/running 백업0건. 현재 Cron도 주간/10분 설정과 일치한다.
- 기존 수동 정상 SQL과 격리 복원 검수는 재사용했다. 이번 주간 파일로 실제 Production 복원을 다시 실행한 것은 아니다.

### 확인할 수 없는 항목과 종료 준비 경계

- CPU 분위수는 이번 조회에서 얻었지만 실행 종류별 전체 CPU 적합성 인증으로 쓰지 않는다. DO GB-s·Workflow 과금 step/state 저장은 기존 미관측 한계가 남는다.0으로 기록하지 않는다.
