# 개발 방식 감사 — 2026-09-28

**판정: 개발 방식에 실질적인 문제가 있다.** 구현이 가짜였다는 증거는 없지만, 내부 구조 우선·지나친 작업 분할·늦은 실제 연결 검증·완료 범위 관리 실패가 겹쳤다. 사용자에게 보이는 완성도보다 저장 계약과 검사 수가 먼저 증가했다. 현 방식을 그대로 유지할 근거는 없다. 사용자의 능력이나 결제 등급 부족으로 설명할 근거도 없다.

이번 요청은 감사다. P5-70/Phase 5는 진행 중이며 구현 재개를 보류한다. 새로운 작업 번호나 제품 요구를 만들지 않았다. 제품 코드·migration·실제 자료·키·원격 환경은 변경하지 않았다. 아래 개선안은 요구사항 삭제나 유료 실행 승인이 아니다.

## 확인된 문제

### 높음 — 실제 한 편 완성보다 내부 구조를 먼저 완성했다

[보관 STATUS](archive/2026-09-21-p5-48/docs/STATUS.md)의 P5-31~47은 17개 작업에 걸쳐 job/receipt, 결과/usage, 사람 검수 저장, bridge, lifecycle/context, domain 계약을 쌓았다. 그 시점 Content Workflow는 실제 생성에 연결되지 않았다. P5-51에서 전체 로컬 Workflow, P5-54에서 발행, **P5-65에서야 새 설교 등록 진입점**을 연결했다. P5-64 통합 검사도 이미 만들어진 설교를 전제로 했다고 [기록](work/P5-64.md)에 명시한다.

이는 “등록 → 실제 AI 초안 → 검수 → 발행 → 풀이”의 가장 짧은 흐름을 일찍 확인한 순서가 아니다. 동시 제출·정답 비공개·과금 중복 방지 같은 보호는 필요하지만, 첫 실사용 결과 전에 모든 이력/호환/원자 저장 구조를 넓게 완성한 순서는 부적절했다. **구현 단위의 완료를 제품 동작의 완료처럼 전달한 진행 관리가 핵심 문제다.**

### 높음 — MVP라는 설명과 실제 완료 명세의 범위가 맞지 않는다

[PROJECT_CONTEXT](PROJECT_CONTEXT.md)는 관리자 1명, 주간 방문 약 30명, 제출 10~20명을 전제한다. 하지만 [v1 완료 정의](spec/release.md)는 수정본 교체·성적 보존·제출 숨김/복원·통합 비용 대시보드·R2 백업·다양한 출력을 모두 요구한다. [운영 명세](spec/architecture.md)는 별도 매뉴얼과 서비스별 사용량 조회도 포함한다.

이 중 여러 요구는 DECISIONS에 확정되어 있다. 모두 AI가 멋대로 추가했다거나 사용자가 잘못 기획했다고 단정할 수 없다. 문제는 넓어진 v1과 먼저 써볼 최소 버전을 분리하지 않은 채, “MVP가 곧 끝난다”는 기대와 긴 구현 목록을 함께 유지한 것이다. 필요 없는 기능을 이번 감사에서 임의 삭제하지 않았다.

또한 “실제 AI 품질과 운영 판단만 남았다”는 STATUS의 Phase 5 설명은 부족했다. 명세에 Phase 5라고 적힌 금지어 관리 화면조차 아직 연결되어 있지 않다. 아래 전체 대조표 없이 남은 작업 번호나 완료일을 말해서는 안 된다.

### 높음 — 이전 감사의 결론이 진행 규칙으로 충분히 정착하지 않았다

[9월 21일 개발 방식 검토](DEVELOPMENT_REVIEW.md)는 이미 내부 구조 우선, 가정한 극단 사례, 반복 문서화, 대량 미커밋을 지적했다. 문서 재구성과 P5-51 이후 연결은 실제 개선이었다. 그러나 P5-70에서 다시 준비·보관·복구·저장·적용 도구를 여러 turn으로 나눠 진행했고, 현재 실제 분석을 바탕으로 한 완성 퀴즈 한 세트는 없다.

현재 복구 기능은 이미 지출한 응답을 살리는 목적이 있으므로 전부 불필요하다고 할 수 없다. 다만 원래 결과 보존 실패와 AI 문자 위치 오류를 뒤늦게 수습하면서 사용자가 새 단계를 반복 승인하는 상황이 만들어졌다. **번호를 늘리지 않더라도 같은 번호가 무한히 커지면 해결이 아니다.**

### 높음 — 실제 환경 검증과 유료 결과 보존이 늦었다

[P5-70](work/P5-70.md)에 Worker fetch의 redirect 설정 문제, 재부팅 후 `/tmp` 교정안/시험 DB 유실, 분석 응답 보관 전 실패가 기록되어 있다. 재부팅을 걱정한 사용자에게 보존을 약속한 뒤 재준비·재교정이 필요해진 것은 작업 방식의 실패다.

첫 분석 실패 원인은 원응답이 없어 미확정이다. 보관한 재시험에서는 인용 42개는 원문에 있었지만 문자 위치 11쌍이 틀렸다. 문자열 위치를 AI가 정확히 계산하도록 요구했던 계약이 실제 데이터에서 실패했고, 지금은 프로그램이 계산하도록 바꿨다. 정상 내용과 잘못된 위치 때문에 유료 결과를 전체 거절한 것이 실제 재작업으로 이어졌다.

전일 교정 USD 0.216028, 새 교정 USD 0.219664, 분석 USD 0.144688/0.148636은 관측 추정액이며 청구 확정액이 아니다. 과거 unknown 2건을 0으로 만들지 않는다. 현재 영속 자료는 재사용해야 하며 재추출·재교정·재분석부터 시작할 이유가 없다. 보관 파일이 남는 것과 Cloudflare 로그인 유효기간은 별개다.

이번 `pnpm check`는 **실패**했다. unit 273개 통과, Worker 2,046개 중 2,045개 통과/1개 실패다. ### 중간~높음 — 복잡성과 Git 보관 위험이 누적됐다

현재 SQL의 테이블 80개 중 이름 기준 generation_/ai_ 26개, sermon_ 19개, quiz_ 13개다. 소스 약 3.6만 줄 중 저장소 코드 약 6,771줄, 서비스 약 11,824줄, DB schema 등 약 2,451줄로 서버 저장·검증에 큰 비중이 있다. 같은 정보의 현재 상태·이력·출처·호환 검사가 여러 계층에 나타나 변경 비용이 커진다. 이것은 규모 신호이지 모든 trigger가 낭비라는 증명은 아니다.

앱 진입점에서 상대 import로 도달하지 않는 소스 후보 17개에는 옛 generation store/runtime, 이전 final-audit, 진단 probe, 복구 CLI용 service, 타입 선언 등이 섞여 있다. 실제 명령행 사용/호환 목적이 있으므로 자동으로 죽은 코드라 판정하거나 삭제하지 않는다. 기존 경로를 보존하면서 새 경로를 계속 추가해온 유지 비용은 관리해야 한다.

HEAD는 **2026-08-29 `0ab476e`**이고 시작 시 Git 추적 파일은 54개뿐이다. `git status --short`는 추적 수정 28행·미추적 경로 328행이며, 디렉터리를 펼친 목록에는 더 많은 파일이 있다. 현재 결과의 대부분은 로컬 미커밋 상태다. 기록이 없다는 뜻은 아니지만 Git 커밋만으로 현재 앱을 복구할 수 없다. **로컬 commit과 Preview를 배포하는 main push는 별개의 행동**인데 복구 지점 확보가 오래 밀렸다. 이번에는 commit/push를 실행하지 않았다.

### 중간 — 짧아졌던 재개 문서가 다시 이력으로 채워졌다

기본 6문서는 이번 시작에 447줄·36,907문자다. 9월 21일 이전 10,759줄·약 110만 문자보다 개선됐지만, P5-70 한 파일은 647줄·76,977문자다. 목차·PROJECT_CONTEXT·ROADMAP에 같은 경과가 길게 반복되고, P5-70 머리말은 아직 “의도 분석 준비 대기”였다. 현재 STATUS는 실제 복구 적용 대기이므로 안내가 서로 달랐다.

이는 다음 turn이 같은 조사를 반복하거나 오래된 자료로 재시작할 위험이다. 이번에는 현재 위치를 STATUS/HANDOFF로 모으고 오래된 안내 머리말을 정정했다. 과거 검증 기록과 승인 내역은 삭제하지 않았다. 문서가 길다는 사실만으로 토큰 낭비율을 계산하지 않는다.

## 권고하는 진행 방식

1. **현재 한 편을 실제로 끝까지 연결하는 것을 최우선 결과로 고정한다.** 보관 분석을 재사용해 비판/사람 확정 → 요약/두 난도 → 무료 배치 → 로컬 검토/발행/풀이까지 한 흐름으로 묶는다. 필요한 유료 횟수·예산·실제 DB 적용 범위를 구체적으로 한 번 제시하고 승인된 범위 안에서 계속 진행한다. 매 내부 helper·검증기마다 새 승인/번호를 만들지 않는다. 이미 소진된 유료 승인을 재사용하지 않는다.
2. **새 저장/복구 구조 설계를 기본 대응으로 삼지 않는다.** 기존 도구로 현재 복구를 적용하고 분석 없이 비판을 이어가는 실제 장애만 좁게 해결한다. 원문·정답 보호, 사용자 기록 보존, 중복 과금 방지는 유지한다. 전체 재작성이나 80개 테이블 일괄 축소도 하지 않는다.
3. **기존 v1 요구와 먼저 사용해볼 범위를 한 번 구분한다.** 위 미완료 표에서 유지/후속 이월을 정해야 한다. 이월은 사용자 결정 후 spec/DECISIONS에 반영하며, 이전 요구를 몰래 완료 처리하지 않는다. 기능 수보다 각각의 완료 화면·통과 조건을 고정한다.
4. **검사를 사용자 흐름과 맞춘다.** 발견한 시간 의존/화면 불일치를 한 묶음으로 정정하고, 변경한 경로 검사·lint/typecheck를 수행한다. Phase/배포 전 전체 검사, 화면 변경 시 관련 브라우저 검사를 한다. 이번에 실패한 전체 검사를 성공으로 기록하지 않고, 필요 없이 전체 검사를 반복하지 않는다. 실제 AI 시험은 합성 검사와 따로 표시한다.
5. **현재 결과를 Git 복구 지점으로 정리하고 재개 문서는 짧게 유지한다.** 비밀값/개인 자료를 제외한 목적별 로컬 commit을 검토하고, main push/배포는 별개로 다룬다. STATUS는 현재 결과, HANDOFF는 다음 첫 동작만 가리키며 상세 경과를 반복 복제하지 않는다.

완료 예측은 이 범위를 고정하고 현재 한 편의 실제 흐름을 확인한 뒤 근거를 붙여야 한다. 지금 “몇 시간 뒤 확실히 끝난다”, “더 높은 요금제를 쓰면 해결된다”, “전체 코드를 다시 만들자”라고 약속할 근거는 없다.

## 검사 요약과 보존

전체 `pnpm check` 실패, 별도 남은 단계 통과, 브라우저 119통과/6실패/1skip이다. 최종 실행 수치와 문서 검사는 함께 저장한 evidence JSON의 `validation`을 따른다. 검사 실패는 미수정 상태로 인계한다. 이번 감사 중 테스트는 합성 자료/격리 DB로 실행했고 유료 provider 호출·실제 시험 DB 쓰기·원격 migration·배포·발행·출력·stage/commit/push는 하지 않았다. 시작 지문과 종료 파일을 대조해 문서 변경 외 기존 파일 보존을 확인한다.

이 감사의 다음은 또 다른 전면 감사가 아니다. 확인된 문제를 반영해 **현재 결과를 살려 한 편을 끝내는 개발로 전환**하는 것이다. P5-70과 Phase 5는 이를 실행하고 해당 완료 조건을 검증하기 전까지 완료로 표시하지 않는다.
